Part 00 · Before the first line

How a Java Program Runs

Every chapter of this course starts with code we wrote in class. This one starts a step earlier — with the questions nobody asks out loud on the first day. What exactly is a program? Why do we write Java and not English? What does Eclipse do when you press Run? Ten minutes on these now makes everything after it make more sense.

In this lesson
  • How the code you type becomes something a computer can run.
  • The four types we use first — int, double, boolean, String — and how each one is stored.
  • Arithmetic, integer division, %, casting, and why 0.1 is never quite 0.1.
  • Asking questions with <, ==, !=, and combining them with &&, ||, !.
  • The three kinds of mistakes a program can have — and which one is the most dangerous.

What a program is

A computer does not think. It follows instructions — exactly the ones it is given, in exactly the order it is given them, billions of times a second. A program is a list of those instructions.

The hard part is the language. Human languages are full of sentences that mean two things at once: “I saw the man with the telescope” — who has the telescope? A person works it out from context. A computer cannot, so we write to it in a programming language: a language with strict rules, where every line can be read in only one way. Java is one of them.

Java, and the machine in the middle

Deep down, a processor understands only machine code — long rows of numbers, and a different set of numbers for each family of chips. A program written directly in machine code is slow to write, almost impossible to read, and runs on one kind of computer only.

Java was designed at Sun Microsystems by a team led by James Gosling and released in 1995 with a clever way around this. Your Java code is not translated for your processor. It is translated into bytecode: machine code for an imaginary computer called the Java Virtual Machine (JVM). Every real computer — Windows, macOS, Linux, even many phones — gets its own JVM, and the JVM runs the bytecode. Write the program once, and it runs everywhere a JVM exists. That promise is the reason Java became one of the most used languages in the world.

One source file, one translation, any computer. The step in the middle is done by the compiler; it is also the step that refuses to continue when your code breaks a rule.

You never see most of this happen. Eclipse is an IDE — an integrated development environment: an editor, the compiler and the JVM in one window. It compiles your file every time you save it, which is why a red underline can appear before you ever press Run: that is the compiler, already complaining.

History

Java was first called Oak, after a tree outside Gosling's office. The name was already taken, so the team renamed it after the coffee they drank — coffee from the island of Java. That is why this page's icon is a cup.

The shape of every file

Every file we wrote in class has the same frame around it. Here is the smallest one that still runs:

Lesson1.java, stripped down
package Grup1;                    // the folder this file lives in

public class Lesson1 {            // must match the file name: Lesson1.java

    public static void main(String[] args) {    // the program starts here

        System.out.println(3);    // one statement, ending with ;

    }
}
Console
3
  • main is the front door. Java starts at the first line inside main and works downwards, one statement at a time, until it reaches the closing brace.
  • A statement ends with a semicolon. The semicolon is the full stop of Java: it tells the compiler where one instruction ends and the next begins.
  • Braces come in pairs. Every { has a } that closes it. Indenting the lines between them is not required — but without it, nobody can see which brace closes which.
  • System.out.println(…) prints whatever is inside the parentheses on the console, then moves to the next line.
  • Java is case-sensitive. System and system are different words. Write the second one and the compiler stops with package system does not exist.

The words class, public, static and void each get a chapter of their own later on. For now they are the frame the picture sits in — the code that matters goes inside main.

Every programmer makes mistakes, every day. What matters is knowing which kind you are looking at, because each kind shows up at a different moment — and one of them never shows up at all.

The most common compile-time error there is

The compiler is strict, but it is on your side: it catches the mistake before anyone runs the program. A logic error gets no such help. The code is perfectly legal Java; it just does not do what you meant. That is why this page keeps showing the console output next to the code — the only way to catch a logic error is to know what the answer should be and check.

History

In 1947, engineers working with Grace Hopper on the Harvard Mark II computer found a moth stuck in one of its relays. They taped it into the logbook with the note “first actual case of bug being found.” Engineers had called faults “bugs” before — but since then, finding and removing them has been called debugging.

In short

You write source code (.java); the compiler checks it and turns it into bytecode (.class); the JVM runs the bytecode on any computer. A program starts in main and runs top to bottom. Mistakes come in three kinds: the compiler catches compile-time errors, the program crashes on run-time errors, and nobody warns you about logic errors.

Part 01 · Lesson1.java

Variables and Data Types

A variable is a named box that holds one value. Every variable you make in Java follows the same three-part pattern, and the type you pick decides what is allowed in the box.

Pattern
// comment line
// TYPE NAME = VALUE ;

int age = 5;

Two slashes start a comment. Java ignores everything after them on that line, so comments are where you explain the code to yourself and to whoever reads it next.

What a variable really is

“Box” is a good picture, and it is closer to the truth than it sounds. A computer's working memory — its RAM — is billions of tiny cells, each holding a 0 or a 1. When Java reaches the line int age = 5;, it does three things:

  1. sets aside enough cells for one int (32 of them),
  2. remembers that this piece of memory is called age,
  3. writes 5 into it.
ageint · 32 bits
value5
ydouble · 64 bits
value3.5
isPositiveboolean
valuetrue
wordString
value"computer science"

Each variable is a name, a type and a value. The name never changes, the type never changes — only the value can.

Two words describe that one line. Writing the type and the name — int age — declares the variable: it tells Java the box exists. Giving it its first value — = 5 — initializes it. Our pattern does both in one statement.

Rule

In Java, = does not mean “is equal to”. It means “work out the right-hand side, then put the result in the box on the left.” It is an instruction, not a statement of fact. Asking whether two things are equal is a different symbol, ==, and it comes in Part 2.

Naming a variable

Names in Java follow two sets of rules. The first set is enforced by the compiler — break one and the program does not compile:

  • A name may contain letters, digits, _ and $ — nothing else, and no spaces.
  • It may not start with a digit.
  • It may not be one of Java's reserved words — int, double, boolean, class, public, static, void, package, true, false and about forty more. These words already mean something to Java.
  • Upper and lower case are different letters: age and Age are two different variables.
Three names the compiler refuses
// int 2nd = 3;       // starts with a digit
// int my age = 6;    // a space in the middle
// int double = 4;    // double is a reserved word
Compiler
error: not a statement
error: ';' expected
Same letters, different case, different variables
int Age = 1;
int age = 2;

System.out.println(Age + age);
Console
3

The second set is enforced by people. Java programmers everywhere write names in camelCase: start with a lowercase letter, and begin every following word with a capital — age, birthYear, isPositive. The bumps in the middle are the camel's humps. And a name should say what is in the box: price beats p, and p beats x. Short names like x and y are fine in a five-line example; in a real program, nobody — including you, a month later — will remember what they meant.

int — whole numbers

int holds whole numbers, positive or negative. No decimal point is allowed.

int
int age = 5;
int year = 2026;
int number = -32432;

An int is stored in 32 bits, and those 32 bits can only spell out so many different numbers. That gives it a fixed range: from -2^31 up to 2^31 - 1.

The limits of int
// 32 bit   2^31-1   -2^31

int max = 2147483647;    // the largest int
int min = -2147483648;   // the smallest int

Why the limit is 2,147,483,647

That number looks random, but it comes straight from those 32 bits. A bit is one cell of memory: it is either 0 or 1. One bit can tell two things apart. Two bits can make four patterns — 00, 01, 10, 11. Every extra bit doubles the count, so n bits make 2n patterns.

Imagine an int with only three bits. That is 23 = 8 patterns, and Java splits them in half: if the first bit is 1, the number is negative.

0000
0011
0102
0113
100−4
101−3
110−2
111−1

Four patterns for the negatives (−4 to −1), four for the rest (0 to 3). The positive side ends one sooner because 0 takes one of its places.

Now do the same with 32 bits. That is 232 = 4,294,967,296 patterns. Half of them, 231, are negative: −1 down to −2,147,483,648. The other half are 0 and the positives: 0 up to 2,147,483,647 — one short, again, because of the zero. That is all -2^31 and 2^31 - 1 mean.

One past the limit does not even compile
int big = 2147483648;
Compiler
error: integer number too large

Eight bits together are called a byte, so an int takes 4 bytes. What happens when a calculation — not a typed number — goes past the limit is a story for Lesson 2: arithmetic overflow.

double — numbers with a decimal point

double holds numbers that have a fractional part.

double
double y = 3.5;
double z = 12321.46457567;
double k = -12312.4535;

A whole number fits inside a double without any trouble — Java just stores it with a decimal part of zero. The other direction does not work: a double may carry a fraction, and there is nowhere in an int to keep it, so Java refuses to compile.

One direction only
double n = 3;      // fine — stored as 3.0

// int m = 3.0;    // ERROR! a double does not fit in an int
Watch out

Small box into big box is automatic. Big box into small box is an error — unless you force it, which is what casting in Part 2 is for.

A double takes 64 bits — twice an int — and spends them differently: some bits hold the digits, others say where the decimal point goes. That is how it reaches numbers far bigger than any int. The price is precision: a double is exact to only about 15–16 digits. Part 2 shows what that price looks like.

boolean — true or false

A boolean has exactly two possible values: true and false. You can write one down directly, or you can store the answer to a question.

boolean
boolean isPositive = true;
boolean isValid = false;

boolean x = 3 > 10;    // the question is answered first,
                       // then the answer goes in the box

System.out.println(x);
Console
false

This is worth pausing on. Java works out 3 > 10 before the assignment happens. Three is not greater than ten, so the result is false, and that is what lands in x.

Good names for booleans read like a yes/no question: isPositive, isValid, hasPassed. When you later read “is positive? true”, the line explains itself.

String — text

A String is text inside double quotes. Anything inside those quotes is text — letters, digits, slashes, symbols, spaces.

String
String word = "computer science";
String password = "abc123";
String date = "24/08/2026";
String numbers = "12345";           // text, not a number
String symbols = "^'+%&/&+%^'";
Watch out

"12345" is not the number 12345. It looks like a number to you, but to Java it is five characters of text, and it behaves like text.

Primitive and not primitive

The four types split into two groups, and this split will matter more and more as the course goes on.

Notice that the three primitive types are written in lowercase, and String starts with a capital letter. That capital is a hint that String is a different kind of thing.

3, 3.0, "3" and true

A value typed straight into the code is called a literal. The way you write it decides its type — Java does not guess from what it looks like to you.

Choosing a type

Before you write a variable, ask what kind of thing it holds. Most of the time the answer is obvious:

InformationExampleType
a person's age16int
the price of a simit17.5double
is the shop open?falseboolean
a city"İzmir"String
a phone number"05321234567"String

The last row is the interesting one. A phone number is made of digits, so why not an int? Three reasons. Nobody ever adds two phone numbers together. The leading 0 would disappear, because the number 05321234567 is just 5321234567. And 5,321,234,567 is bigger than 2,147,483,647 — it does not fit in an int at all.

Rule of thumb

If you will never do arithmetic with it, it is probably text. Phone numbers, ID numbers, postcodes and student numbers with leading zeros are Strings, even though they are made of digits.

In short

A variable is a named piece of memory with a fixed type. int holds whole numbers in 32 bits (−2,147,483,648 to 2,147,483,647); double holds decimals in 64 bits; boolean holds true or false; String holds text and is not primitive. A smaller type goes into a bigger one on its own, never the other way. Names are camelCase and say what they hold.

Part 02 · Lesson2.java

Operators, Casting and Number Traps

Part 1 was about storing values. This part is about doing something with them. Two words first, because every book and every exam question uses them: an operator is a symbol that does a job, like + or <; the values it works on are its operands. Put them together — x / y, 3 > 10 — and you have an expression: any piece of code that produces a value. Most of the surprises in this part come from one fact: the type of the operands decides the type of the answer.

Arithmetic operators

Java gives you five: +, -, *, / and %. The last one is called mod (modulus) and it hands you the remainder of a division.

The + operator does a second job as well. Put it between two Strings and it glues them together.

Plus with Strings
String a = "A";
String b = "B";

System.out.println(a + b);
Console
AB

Order of operations

When several operators appear in one expression, Java does not simply work left to right. It follows a priority list:

  • 1. parentheses
  • 2. *, /, %
  • 3. +, -
Priority in action
System.out.println(2 + 3 * 4);      // 3*4 happens first
System.out.println((2 + 3) * 4);    // parentheses jump the queue
Console
14
20

Mod

% gives the remainder. Divide, throw away the quotient, keep what is left over.

Mod
System.out.println(15 % 4);    // 4 fits 3 times, 3 left over
System.out.println(14 % 2);    // divides exactly, nothing left
System.out.println(7 % 3);     // 3 fits 2 times, 1 left over
System.out.println(5 % 12);    // 12 does not fit at all
Console
3
0
1
5

That last line surprises people. When the left number is smaller than the right one, nothing can be taken out of it, so the whole number is the remainder.

One step at a time

When an expression mixes operators, Java follows the order from the file: parentheses first, then *, /, %, then +, -. Operators on the same level go left to right. Here is a long one, solved the way Java solves it:

2 + 17 % 5 * 3 - 4 / 3
// 2 + 17 % 5 * 3 - 4 / 3
// 2 +    2   * 3 - 4 / 3     17 % 5 is 2      (first of * / % from the left)
// 2 +        6   - 4 / 3     2 * 3 is 6
// 2 +        6   -   1       4 / 3 is 1       (int division)
//     8          -   1       now + and -, left to right
//          7

System.out.println(2 + 17 % 5 * 3 - 4 / 3);
Console
7

Doing this on paper, one line per step, is exactly how you should attack an expression question on the exam. Skipping steps in your head is where the mistakes hide.

What % is good for

% looks like a strange extra, but it answers questions you meet every day. Whenever something is counted in groups — minutes into hours, students into teams, days into weeks — / tells you how many full groups, and % tells you what is left over.

Groups and leftovers
int minutes = 135;
System.out.println(minutes / 60);    // full hours
System.out.println(minutes % 60);    // minutes left over

int students = 17;
System.out.println(students / 5);    // full teams of 5
System.out.println(students % 5);    // students without a team
Console
2
15
3
2

A 135-minute film lasts 2 hours 15 minutes. Seventeen students make 3 teams of five, with 2 left over. Two more tricks come up again and again:

Even numbers and last digits
System.out.println(47 % 2 == 0);    // even? an even number leaves 0
System.out.println(2026 % 10);      // the last digit
Console
false
6

Every whole number divided by 2 leaves 0 or 1, so n % 2 == 0 asks “is n even?”. And dividing by 10 leaves exactly the last digit — an idea Lesson 3 uses to take whole numbers apart, digit by digit.

Watch out

With a negative number on the left, the remainder is negative too: -7 % 3 is -1, not 2. The sign of the answer follows the left-hand number. Most problems keep to positive numbers, but now you know.

Integer division

Divide an int by an int and Java gives you an int back. The fractional part is not rounded — it is thrown away.

17 divided by 5
int x = 17;
int y = 5;

System.out.println(x / y);       // not 3.4

double answer = x / y;
System.out.println(answer);
Console
3
3.0
Watch out

Declaring answer as a double does not save you. The division on the right runs first, with two ints, and produces 3. Only then is that 3 copied into a double box and becomes 3.0. The 0.4 was already gone before the assignment happened.

Casting

To keep the fractional part, one of the two numbers has to be a double before the division. Writing (double) in front of a value forces Java to treat it as one. That is a cast.

Four attempts, one failure
System.out.println((double) x / y);            // 17.0 / 5
System.out.println(x / (double) y);            // 17 / 5.0
System.out.println((double) x / (double) y);   // 17.0 / 5.0
System.out.println((double) (x / y));          // (double) 3
Console
3.4
3.4
3.4
3.0

The first three all work, and it only takes one of the two numbers to be a double — the other is promoted automatically. The fourth one fails, and the only difference is where the parentheses are.

Watch out

In (double) (x / y) the parentheses tell Java to divide first. Two ints go in, 3 comes out, and only that 3 gets cast. You are casting the answer instead of the inputs, and by then it is too late.

Casting the other way

You can also cast a double down to an int. This is the one Java would not do on its own back in Part 1 — the cast is you taking responsibility for the loss.

(int) cuts, it does not round
double value = 3.89;
double value2 = 3.19;

System.out.println((int) value);
System.out.println((int) value2);
Console
3
3

3.89 does not become 4. The cast chops off everything after the decimal point and keeps the whole part, no matter how close to the next number you were.

When an int meets a double

Every operator looks at its two operands before it does anything. The rule is short:

OperandsAnswerExampleResult
int and intint17 / 53
int and doubledouble17 / 5.03.4
double and intdouble7 + 2.09.0

When the types differ, Java quietly turns the int into a double first — small box into big box, just like in Part 1. This is called promotion (or widening), and it is why one cast was enough above.

But Java promotes one operator at a time, from left to right. A double later in the line cannot rescue a division that already happened:

Same numbers, different order
System.out.println(1 / 2 * 4.0);    // 1 / 2 first: two ints, so 0
System.out.println(4.0 * 1 / 2);    // 4.0 * 1 first: a double from the start
Console
0.0
2.0

Rounding with a cast

(int) cuts. But one small trick turns cutting into rounding: add 0.5 first.

Add a half, then cut
System.out.println((int) (3.89 + 0.5));    // (int) 4.39
System.out.println((int) (3.19 + 0.5));    // (int) 3.69
Console
4
3

Anything with a fraction of .5 or more is pushed past the next whole number before the cut, so it ends up there. Anything below .5 is not pushed far enough, so it falls back. The parentheses matter: the 0.5 has to be added before the cast, not after.

Watch out

The trick is for positive numbers. (int) (-3.89 + 0.5) is (int) -3.39, which gives -3 — but −3.89 rounds to −4. For a negative number, subtract the half instead: (int) (-3.89 - 0.5) gives -4.

Dividing by zero

Dividing an int by zero is not something Java can do, and it is not something the compiler catches either. The code compiles fine and the program starts fine — then it crashes at the moment it reaches that line. That is a run-time error, and this one is called an ArithmeticException.

ArithmeticException
int number1 = 12;
int number2 = 0;

// System.out.println(number1 / number2);   // ArithmeticException
// System.out.println(number1 % number2);   // ArithmeticException

Both / and % crash, because both of them have to divide to do their job.

Asking questions
int c = 3;

== and != are listed for int only, and that restriction is deliberate. The next section shows what happens when you ignore it.

Round-off error

A double does not store a number exactly. It stores something extremely close to it. Almost always that is close enough — until you compare two doubles that should be equal.

Two ways to reach 0.7
double val1 = 0.6;
double val2 = 0.8;

double val3 = val1 + 0.1;    // 0.6 + 0.1, so 0.7
double val4 = val2 - 0.1;    // 0.8 - 0.1, so 0.7

System.out.println(val3 == val4);
System.out.println(val3);
System.out.println(val4);
Console
false
0.7
0.7000000000000001

Both calculations should land on 0.7. One of them lands a tiny distance away, and == has no tolerance for tiny distances — it wants the two values identical, bit for bit. So the answer is false, and the console shows you exactly where the extra amount came from.

It is not that doubles can never be equal. Two doubles that were never calculated, only written down, match perfectly:

Same value, written twice
double val5 = 23435.6765765;
double val6 = 23435.6765765;

System.out.println(val5 == val6);
Console
true

The damage comes from arithmetic. Each operation can nudge the value a little, and those nudges are what == trips over.

Why a double cannot hold 0.1

Try to write one third as a decimal. 0.3, 0.33, 0.333… — however many 3s you write, you have to stop somewhere, and wherever you stop, you are a tiny bit short. Some fractions simply do not fit in base 10.

A computer counts in base 2, and in base 2 the troublemaker is one tenth. Written in bits, 0.1 is 0.000110011001100110011… — the 0011 repeats forever. A double has 64 bits, so it has to stop, and the 0.1 it stores is a hair away from the real 0.1. Usually Java hides that hair when it prints. Arithmetic can make it big enough to show:

Where the hair shows
System.out.println(0.1 + 0.2);
System.out.println(1.0 / 3);
Console
0.30000000000000004
0.3333333333333333

That is the whole story of round-off error. It is not a bug in Java — every language that uses the same 64-bit format, which is nearly all of them, prints the same 0.30000000000000004.

In real life

Banks cannot afford a hair here and a hair there across millions of payments. That is why money is usually stored as a whole number of the smallest unit — 1750 kuruş instead of 17.50 lira — in an integer type, where every value is exact.

Try it

Write code that checks whether two double values are equal correctly — in a way that is not fooled by the extra 0.0000000000001. Bring your attempt to class and we will go through it together. We did, in Lesson 5, with Math.abs: the solution is there.

Comparing Strings

Build the text "AB" two different ways, and the two results look identical on screen. Compare them with == and Java says they are not the same.

Identical on screen, not equal to ==
String s1 = "A";
String s2 = "B";
String s3 = "AB";

System.out.println(s1 + s2);
System.out.println(s3);
System.out.println((s1 + s2) == s3);
Console
AB
AB
false

The first two lines print the same three characters. The third line still says false. This is the same lesson as round-off error, arriving from a different direction: == is stricter than "looks the same to me".

Rule

Never use == to compare two Strings. It is not a rule about style — the answer it gives you will be wrong. We will cover the correct way to do it later.

In short

An expression runs in a fixed order: parentheses, then * / %, then + -, left to right within a level. Two ints give an int, so / throws the fraction away and % gives the remainder. One double makes the answer a double. A cast forces a type: (double) on an input saves the fraction, (int) cuts it off. Dividing an int by zero crashes. Doubles are almost never exact, so never compare them with == — and never compare Strings with it either.

Logical Operators

Relational operators turn numbers into true and false. Logical operators take those true and false values and combine them, so you can ask one question made of several smaller questions.

History

The word boolean is a person's name. George Boole (1815–1864), an English mathematician, showed in 1854 that logic — and, or, not, true, false — can be calculated just like arithmetic. For eighty years it was pure mathematics. Then in 1937 Claude Shannon showed that electrical switches follow exactly Boole's rules. Every chip in every phone and computer today is built from billions of tiny AND, OR and NOT switches.

Between two numbers

In maths you write 0 < x < 10 and everybody understands. Java does not:

Maths notation does not compile
int x = 5;

Compiler

Java works left to right: 0 < x becomes true, and then it is asked whether true < 10 — which means nothing. “Between” is really two questions joined with AND:

Two questions, one AND
int x = 15;

Console

In real life

Every form you fill in checks ranges like this. An exam score is valid when score >= 0 && score <= 100. It is invalid when score < 0 || score > 100 — and notice that the second line is exactly the first one, put through De Morgan's Law below.

Short-circuit evaluation

Look at the AND table again. If the left side is already false, the answer is false no matter what the right side says. And in the OR table, if the left side is already true, the answer is true regardless.

Java notices this. When the left side settles the question on its own, the right side is never evaluated at all. It is not that Java evaluates it and ignores the result — it does not run it.

Here is how we proved it. c is zero, so b / c would throw the ArithmeticException from Part 2 the instant it ran. That makes the right side a tripwire: if the program crashes, the right side ran.

The tripwire
int a = 3;
int b = 5;
int c = 0;      // dividing by this crashes
int d = -3;

// System.out.println(a > b && b / c == d);   // false && ...  -> false
// System.out.println(a < b && b / c == d);   // true  && ...  -> crash
// System.out.println(a < b || b / c == d);   // true  || ...  -> true
// System.out.println(a > b || b / c == d);   // false || ...  -> crash
ExpressionLeft sideRight sideResult
a > b && b / c == dfalsenever runsfalse
a < b && b / c == dtruerunscrash
a < b || b / c == dtruenever runstrue
a > b || b / c == dfalserunscrash
Watch out

The very same broken right side is harmless in two of these lines and fatal in the other two. Nothing changed about the danger — only whether the left side made Java bother to look.

Short-circuit on purpose

In class we used short-circuiting to prove a point. Programmers use it every day as a safety guard. Put the check that keeps you safe on the left, and the dangerous part on the right:

The left side protects the right
int b = 5;
int c = 0;

System.out.println(c != 0 && b / c > 2);    // c != 0 is false, so b / c never runs
Console
false

Swap the two sides — b / c > 2 && c != 0 — and the program crashes, because now the division runs first. With && and ||, the order of the two sides is not just style; it can be the difference between an answer and an exception.

De Morgan's Law

Sometimes you need the opposite of a compound condition. Putting a ! in front of the whole thing works, but it is hard to read. De Morgan's Law lets you push that ! all the way inside instead.

Same condition, written twice
// !( a < b && c == d )

//    a >= b  ||  c != d

Two things happen at once when the ! moves inside:

  • Every comparison flips to its opposite — < becomes >=, and == becomes !=.
  • The operator in the middle swaps — && becomes ||.
Watch out

Flipping the comparisons but leaving && in the middle is the mistake almost everyone makes. Both changes have to happen, or the new condition means something completely different.

To flip a comparison, take its exact opposite — the one that is true whenever the original is false. Most people get < wrong the first time: its opposite is >=, not >, because “not less than 5” includes 5 itself.

ComparisonIts opposite
a < ba >= b
a > ba <= b
a == ba != b

In plain words, the law is something you already know. “It is not true that it is cold and raining” means “it is not cold, or it is not raining” — at least one of the two is missing. The law also works the other way round: “it is not true that I have a pen or a pencil” means “I have no pen, and I have no pencil.” Written with P and Q for any two conditions:

This……is the same as
!(P && Q)!P || !Q
!(P || Q)!P && !Q

You do not have to take it on trust. There are only four possible combinations of P and Q, so you can check every one:

PQ!(P && Q)!P || !Q
TTFF
TFTT
FTTT
FFTT

The last two columns match in every row, so the two expressions are the same — always. Checking all the rows like this is called a truth table, and it settles any “are these two the same?” question about booleans.

History

Augustus De Morgan (1806–1871) taught mathematics in London and wrote down these two rules. He and George Boole knew each other and exchanged letters for years — the two men behind this part of the lesson were friends.

In short

&& is true only when both sides are; || when at least one is; ! flips. ! is applied first, && before ||. When the left side already decides the answer, the right side is not run at all — so put safety checks on the left. “Between” is two comparisons joined with &&. De Morgan: moving a ! inside flips every comparison and swaps && with ||.

    Here a < b is false and a > b is true. A false on the left of && and a true on the left of || both settle the question on their own, so the dangerous right side is never reached. In the other two the left side settles nothing, Java goes on to evaluate a / c, and the program dies.

    The opposite of >= is <, the opposite of != is ==, and the && becomes ||.

    The two comparisons were flipped correctly, but the operator in the middle was left alone. It has to change as well:

    This is the mistake to watch for. Half of De Morgan's Law is not a weaker version of it — it is a different condition that happens to look right.
