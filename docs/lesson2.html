Part 04 · Lesson4.java

Assignment Operators, final and Overflow

Lesson 1 created variables and asked questions about them. This lesson makes them move. A variable's value can change as the program runs — that is the whole point of calling it a variable — and once values change, the program can make decisions based on them. Those two ideas, change and choice, are what turn a calculator into a program.

In this lesson
  • Giving a variable a new value, and the shorthands +=, -=, *=, /=, %=, ++, --.
  • Following a variable on paper with a trace table — and swapping two values.
  • final: values that must never change, and why programs name them.
  • What happens when an int runs out of room — and where that has cost real money.
  • if, else, else if: how a program chooses, and the bugs that hide in braces.

Reassigning a variable

Declaring a variable and changing it later are two different things. The type is written once, when the box is created. After that you only use the name.

Declare once, assign as often as you like
int a = 3;               // type name = value ;
System.out.println("a: " + a);

a = 5;                   // name = value ;
System.out.println("a: " + a);
Console
a: 3
a: 5

The old value is gone the moment the new one lands. A variable holds one value, never two.

The right side is worked out first
int b = 8;
b = 11;

a = b;         // a becomes 11
System.out.println("a: " + a);

a = b + 3;     // 11 + 3
System.out.println("a: " + a);

a = a + 5;     // 14 + 5
System.out.println("a: " + a);
Console
a: 11
a: 14
a: 19
Rule

= is not the equals sign from maths. Java works out the whole right-hand side first, then drops the answer into the box on the left. That is why a = a + 5 makes perfect sense to Java and no sense at all as an equation.

Following a variable on paper

Once values change, “what is a now?” depends on when you ask. The reliable way to answer is a trace table: one column per variable, one row per line, and you write down every value the moment it changes. Here is the code above, traced:

LineabPrinted
int a = 3;3–
a = 5;5–
int b = 8;58
b = 11;511
a = b;1111a: 11
a = b + 3;1411a: 14
a = a + 5;1911a: 19

Bold marks the value that changed on that line. Notice a = b: a gets a copy of 11, and b keeps its own 11 — nothing ties the two boxes together afterwards.

Trace tables look slow. They are not — they are the fastest way to get a tracing question right, on paper or on the exam, because they stop you from carrying five changing numbers in your head.

Swapping two values

Here is a puzzle that shows exactly how = works. You have a = 3 and b = 8, and you want them the other way round. The obvious attempt fails:

The obvious swap
int a = 3;
int b = 8;

a = b;      // a is 8 ... and the 3 is gone forever
b = a;      // b gets a's value, which is now 8

System.out.println("a: " + a + "  b: " + b);
Console
a: 8  b: 8

The first line overwrites the 3 before anyone saved it. Think of two full glasses of juice you want to swap: you need a third, empty glass. In code, the empty glass is a third variable, usually called temp:

Swap with a third variable
int a = 3;
int b = 8;

int temp = a;   // keep the 3 safe
a = b;          // a is 8
b = temp;       // b gets the 3 back

System.out.println("a: " + a + "  b: " + b);
Console
a: 8  b: 3

"a: " + a

Every line of this file prints with "a: " + a. In Lesson 1, + glued two Strings together. Here one side is a String and the other is an int — and the rule is: if either side of a + is a String, the other side is turned into text and glued on. That is how a number ends up inside a message.

Like every operator on the same level, + works left to right, and that order decides whether you get arithmetic or gluing:

Left to right decides
System.out.println("a: " + 2 + 3);      // ("a: " + 2) + 3  -> text all the way
System.out.println("a: " + (2 + 3));    // the parentheses add first
System.out.println(2 + 3 + " :a");      // 2 + 3 is maths, then the text
Console
a: 23
a: 5
5 :a

Once the String has joined in, every + after it glues. Before the String arrives, + still adds. When you want a sum inside a message, put the sum in parentheses.

Compound assignment operators

Writing a = a + 2 over and over gets old, so Java gives you a shorthand for each of the five arithmetic operators.

ShorthandMeansReads as
a += 2a = a + 2add 2 to a
a -= 3a = a - 3take 3 away from a
a *= 4a = a * 4multiply a by 4
a /= 2a = a / 2divide a by 2
a %= 3a = a % 3replace a with the remainder

They are not new arithmetic — they are the same five operators with less typing. Follow the value of a down this list, starting from 19:

All five, one after another
int a = 19;

a += 2;    System.out.println("a: " + a);   // 19 + 2
a -= 3;    System.out.println("a: " + a);   // 21 - 3
a *= 4;    System.out.println("a: " + a);   // 18 * 4
a /= 2;    System.out.println("a: " + a);   // 72 / 2
a %= 3;    System.out.println("a: " + a);   // 36 % 3
Console
a: 21
a: 18
a: 72
a: 36
a: 0

The last line lands on 0 because 3 divides 36 exactly, so there is no remainder left over.

Watch out

The shorthand does not rescue you from integer division. Two int values still divide as ints, and the fraction is still thrown away.

Still integer division
int d = 7;
d /= 2;                 // you might read this as 3.5
System.out.println(d);
Console
3

The shorthands work just as well with doubles, which is where they show up in real programs — scores, prices, balances, anything that keeps growing or shrinking:

A 20% price increase
double price = 100;
price *= 1.2;            // price = price * 1.2
System.out.println(price);
Console
120.0
Watch out

The shorthand and the long form are not quite twins. With int x = 7;, the line x = x / 2.0; does not compile — the right side is a double, and a double does not fit in an int. But x /= 2.0; compiles and leaves 3 in x: a compound operator quietly casts the answer back to the variable's type. Quietly is the problem — the 0.5 is cut off without a word.

++ and --

Adding or taking away exactly 1 is so common that it gets its own operator: ++ counts up by one, -- counts down by one.

++ and -- on their own line
int n = 5;
System.out.println(n);

n++;                    // exactly the same as n += 1
System.out.println(n);

n--;                    // exactly the same as n -= 1
System.out.println(n);
Console
5
6
5

So there are three ways to write the same step: n = n + 1, n += 1, and n++. They do exactly the same thing, and ++ is simply the shortest of the three.

Rule

++ and -- only ever change the value by 1. For any other amount you need += or -= — there is no such thing as ++2.

final

Put final in front of a declaration and the box is sealed. It gets one value, and any attempt to change it later is a compile error — Java refuses to build the program at all.

Sealed after the first value
final int x = 5;

x = 10;                 // ERROR
Compiler
error: cannot assign a value to final variable x
        x = 10;
        ^
1 error

This is not Java being difficult. It is a way of writing down a value that should never move, so that the compiler catches you if you ever change it by accident.

Values that have no business changing
final double PI = 3.14;
final double TAX_RATE = 0.2;
final int MAX_VALUE = 2147483647;
final int MIN_VALUE = -2147483648;
Rule

By convention a final variable is named in ALL_CAPS, with underscores between words. Java does not force this, but every Java programmer reading your code expects it — a capitalised name is a promise that the value never moves.

The value a final is sealed with does not have to be typed out. It can be whatever another variable happens to hold at that moment — and it is a copy, frozen right there.

Frozen at the moment of the assignment
int y = 5;
y = 12;
y = 3;

final int z = y;        // z takes the value 3

y = 99;                 // y is free to keep moving
System.out.println("z: " + z + "   y: " + y);
Console
z: 3   y: 99

z is not tied to y. It copied the number 3 and then stopped listening.

Why name a number at all

You could type 0.2 straight into every calculation instead of declaring TAX_RATE. Programmers call a bare number like that a magic number — it works, but nobody reading the code knows what it means, and nobody can change it safely.

The number has a name
final double TAX_RATE = 0.2;
double net = 250;

System.out.println(net * TAX_RATE);          // the tax
System.out.println(net + net * TAX_RATE);    // the price with tax
Console
50.0
300.0

Two things are better now. The line reads like a sentence: net times tax rate. And when the rate changes — tax rates do — you change one line at the top, not every 0.2 scattered through the program. Worse, some of those 0.2s might not have been the tax rate at all.

Arithmetic overflow

Back in Lesson 1 we said an int lives in 32 bits, and that this gives it a fixed range. Now we find out what happens when a calculation walks off the end of that range.

32 bits can spell out 232 = 4,294,967,296 different patterns — no more. Java hands out half of them to negative numbers and half to zero-and-up, which is where the two limits come from:

The two ends of the range
int min = -2147483648;   // -2^31    the smallest int
int max =  2147483647;   //  2^31-1  the largest int

There is no pattern left over for "one more than the largest". So what does Java do when you ask for it?

One past the top
int num = 2147483647;

System.out.println(num + 1);

num *= 2;
System.out.println(num);
Console
-2147483648
-2

It wraps around. Think of the odometer in a car, or the hour hand on a clock: when the digits run out, they do not stop and they do not grow an extra column — they roll over to the beginning. Adding 1 to the largest int lands you on the smallest one.

The second line is the same effect, further around the dial. 2147483647 × 2 is 4,294,967,294, which is 2 short of the 4,294,967,296 patterns that exist — so counting that far around the ring leaves you 2 short of where you started, at -2.

The ring, from both directions
int max = 2147483647;
System.out.println(max + 1);      // over the top
System.out.println(max + 2);      // and one further

int min = -2147483648;
System.out.println(min - 1);      // under the bottom
Console
-2147483648
-2147483647
2147483647
Rule

Overflow produces no error, no warning and no exception. The program keeps running happily with a wrong number in it. This is the reason it is worth memorising: nothing will tell you it happened except the nonsense in your output.

Overflow does not need a giant number in the code. It only needs a calculation whose answer is too big — and the multiplication runs in int before anything is stored:

How many seconds in 70 years?
int seconds = 70 * 365 * 24 * 60 * 60;
System.out.println(seconds);    // should be 2,207,520,000
Console
-2087447296

A human life does not fit in an int — not when it is counted in seconds. Every factor is small; only the answer is too big.

In real life

Gangnam Style, 2014. YouTube stored view counts in a 32-bit integer. When the video approached 2,147,483,647 views, YouTube had to switch to a bigger number type before the counter wrapped to a negative number.

Ariane 5, 1996. Thirty-seven seconds after its first launch, the European rocket broke apart. A value from its guidance software was squeezed into an integer type too small to hold it; the conversion failed, and the navigation system shut down.

The year 2038. Many computers count time as seconds since 1 January 1970, in a 32-bit int. That count reaches 2,147,483,647 at 03:14:07 UTC on 19 January 2038. One second later, a computer that has not been updated will think it is December 1901.

In short

= overwrites: the old value is gone. Trace changing values in a table, one row per line. Swapping needs a third variable. The compound operators (+= … %=) and ++ / -- are shorthands, but integer division still cuts. In a + with a String, the other side becomes text. final seals a value; name such constants in ALL_CAPS instead of scattering magic numbers. An int that goes past its limit wraps around silently.

Part 05 · Lesson5.java

Control Structures: if and else

Everything we have written so far runs top to bottom, every line, every time. A control structure is what lets the program choose — and the first one is if.

A fork in the road

Until now every program was a straight line: Java ran line 1, then line 2, then line 3, to the end. The order in which statements run is called the flow of control, and an if is the first thing that bends it. Programmers often draw it as a flowchart: a diamond for the question, arrows for the answers.

One question, two roads, and the roads meet again underneath. With number = 6 the program takes the left road; the right one is skipped entirely.

The shape of an if

The full pattern
if (condition)
{
    action
}
else if (condition2)
{
    action2
}
else
{
    action3
}

What goes in the parentheses has to be a boolean — something that is either true or false. That is exactly what the relational and logical operators from Lesson 1 produce, which is why we did those first.

Even or odd
int number = 6;

if (number % 2 == 0)
{
    System.out.println("Even number!");
}
else
{
    System.out.println("Odd number!");
}
Console
Even number!

number % 2 is the remainder after dividing by 2, and comparing it to 0 answers the question "does 2 divide this exactly?". Exactly one of the two branches runs — never both, never neither.

Since a condition is just a boolean, you can work it out first and keep it in a variable. With a good name, the if reads like English:

A condition with a name
int number = -5;
boolean isEven = number % 2 == 0;

if (isEven) {
    System.out.println("even");
}
else {
    System.out.println("odd");
}
Console
odd

Write if (isEven), not if (isEven == true). Both work, but the second asks “is it true that it is true?” — isEven already is the answer.

Braces: when they are required, and what happens without them

The braces are required as soon as the if controls two or more lines. For a single line they are optional, and Java will not complain if you leave them out.

That optional-ness is the trap. Leave the braces off and write two lines anyway, and only the first one belongs to the if. The second is an ordinary line that runs no matter what.

No braces, two lines
int number = -4;

if (number > 0)
    System.out.println("Positive");
    System.out.println("Positive!");
Console
Positive!

The number is negative, and the word Positive! still appears. Indentation is for human eyes — Java ignores it completely. What Java actually read is this:

How Java reads the same code
if (number > 0)
    System.out.println("Positive");

System.out.println("Positive!");    // never belonged to the if

Put the braces in and the second line joins the first inside the if. Now the negative number silences both:

With braces, same value
int number = -4;

if (number > 0)
{
    System.out.println("Positive");
    System.out.println("Positive!");
}
Console
(nothing)
Rule

Write the braces every time, even for a single line. They cost two characters and they remove this entire category of bug — including the dangling else waiting for us in Part 6.

In real life

In 2014, Apple found a bug in the code that checks secure connections on iPhones and Macs. An if without braces was followed by a line that had been typed twice by accident. The copy looked indented under the if, so it looked harmless — but, exactly like "Positive!" above, it ran every time and skipped the security check that came after it. Millions of devices were affected until the update. It became known as the goto fail bug, after the line that was repeated.

The semicolon that ends an if

A semicolon ends a statement — and a semicolon on its own is a statement too, one that does nothing. Put one straight after the condition, and that empty statement becomes the whole body of the if:

One character too many
int number = -5;

if (number > 0);           // the if ends here, doing nothing
{
    System.out.println("Positive");    // an ordinary block — always runs
}
Console
Positive

It compiles, it runs, and −5 is called positive. When an if seems to be ignored completely, look at the end of its line first.

Watch out

Writing = where you meant == is a classic slip. Java at least catches it here: if (x = 5) does not compile — incompatible types: int cannot be converted to boolean — because x = 5 is an assignment, and its result is a number, not a yes-or-no answer.

else

else has no condition of its own. It is the branch that runs when the if above it was false, and nothing else needs to be checked.

Two branches, one of them always runs
int number = 6;

if (number > 0) {
    System.out.println("Positive");
}
else {
    System.out.println("Not Positive");
}
Console
Positive

Nested if versus else if

Two branches are often not enough. A number can be positive, negative or zero — three answers. One way to get there is to put a whole second if inside the else:

An if inside an else
int number = 1;

if (number > 0) {
    System.out.println("Positive");
}
else {
    if (number < 0) {
        System.out.println("Negative");
    }
    else {
        System.out.println("Zero");
    }
}
Console
Positive

It works, but every extra answer pushes the code further to the right. Java lets you drop the braces around that inner if and pull it back onto the else line:

The same three branches, written flat
int number = 1;

if (number > 0) {
    System.out.println("Positive");
}
else if (number < 0) {
    System.out.println("Negative");
}
else {
    System.out.println("Zero");
}
Console
Positive
Watch out

else if is not a new keyword. It is an ordinary else whose action happens to be another if — the two versions above are the same program, just typed differently. Knowing that is what makes the dangling else in Part 6 make sense.

An if in the real world

Every app you use is full of ifs. A cash machine is a good one to imagine — and it combines this part with Part 4, because the balance only changes in one of the two branches:

A cash machine, twice
int balance = 500;
int amount = 200;

if (balance >= amount) {
    balance -= amount;
    System.out.println("Take your cash. Left: " + balance);
}
else {
    System.out.println("Not enough money. Left: " + balance);
}

amount = 400;    // the same code again, with a bigger request
// ... same if / else ...
Console
Take your cash. Left: 300
Not enough money. Left: 300

The second request fails, and the balance stays 300 — the -= sits inside the branch that did not run. Where a line is placed decides whether it happens, not just when.

In short

An if runs its body only when its condition — any boolean — is true; an else runs when it is false, so exactly one of the two runs. Braces decide what belongs to an if; indentation does not. Write them every time. A semicolon right after the condition empties the if. else if is an else whose body is another if.

  5. Here is a test for odd numbers. It works for 7 and fails for -7. What does it print for each, and why?

    if (number % 2 == 1) {
    System.out.println("Odd");

    System.out.println("Even");
}

    7 gives Odd. -7 gives Even, which is wrong.

    In Java -7 % 2 is -1, not 1 — the remainder keeps the sign of the left-hand number. So the condition is false and the else runs.

Part 06 · Lesson6.java

else if Chains and the Dangling else

A grade from a number

Turning a mark out of 100 into a grade from 1 to 5 needs five branches, plus one more for a mark that is not a valid mark at all.

The whole chain
int note = -243;

if (note < 0 || note > 100) {
    System.out.println("INVALID NOTE!!");
}
else if (note >= 80) {
    System.out.println("5");
}
else if (note >= 60) {
    System.out.println("4");
}
else if (note >= 40) {
    System.out.println("3");
}
else if (note >= 20) {
    System.out.println("2");
}
else {
    System.out.println("1");
}
Console
INVALID NOTE!!

Two things are worth stealing from this chain.

The validity check comes first. Rejecting nonsense before any real work happens means none of the branches below have to worry about it. That is what || from Lesson 1 is doing there: too small or too big, either one is enough to reject.

Each branch only sees what the ones above rejected. note >= 60 looks like it should catch 85 as well — and on its own it would. But 85 was already taken by the branch above, so by the time Java reaches this line it is really asking "is it 60 to 79?". This is why the chain has to run from the highest boundary down.

Same chain, four different marks
// note = 100  ->  5
// note =  80  ->  5
// note =  79  ->  4
// note =   0  ->  1
Console
5
5
4
1

0 falls all the way through to the final else — it is a legal mark, so the first branch does not reject it, and it clears none of the four boundaries.

Testing a chain

How do you know the grade chain is right? Running it once with a random number proves almost nothing. Bugs in chains live at the boundaries — the exact numbers where one branch hands over to the next. A > typed where >= was meant changes the answer for 80 and for no other mark.

So professional testers pick their values on purpose: each boundary, one below it, one above it, and the values that should be rejected.

noteWhy test itExpectedGot
79just below the 80 boundary44
80the boundary itself55
81just above it55
0the smallest valid mark11
100the largest valid mark55
-1one below the valid rangeINVALID NOTE!!INVALID NOTE!!
101one above the valid rangeINVALID NOTE!!INVALID NOTE!!

Write the Expected column before you run anything. A test is only a test if you decided the answer first.

A chain from real life

Cinema prices by age: under 6 free, under 18 student price, 65 and over senior price, everyone else full price.

Ticket price
if (age < 6) {
    System.out.println(age + " -> free");
}
else if (age < 18) {
    System.out.println(age + " -> 60 TL");
}
else if (age >= 65) {
    System.out.println(age + " -> 50 TL");
}
else {
    System.out.println(age + " -> 120 TL");
}

// run with age = 4, 15, 30 and 70
Console
4 -> free

30 -> 120 TL
70 -> 50 TL

Look at the second branch: it says age < 18, not age >= 6 && age < 18. It does not need to — anyone under 6 was already taken by the first branch. The chain does half the work for you, as long as the order is right.

Separate ifs are not a chain

Now take the else out of every line. The code still compiles, still looks like a chain, and does something completely different.

Four separate ifs
int note = 85;

if (note >= 80) System.out.println("5");
if (note >= 60) System.out.println("4");
if (note >= 40) System.out.println("3");
if (note >= 20) System.out.println("2");
Console
5
4
3
2

Four separate if statements are four separate decisions. Java checks every single one, top to bottom, and runs every one whose condition is true. 85 clears all four boundaries, so all four print.

The same conditions, joined by else
int note = 85;

if (note >= 80) System.out.println("5");
else if (note >= 60) System.out.println("4");
else if (note >= 40) System.out.println("3");
else if (note >= 20) System.out.println("2");
Console
5
Rule

Separate if statements run independently — Java checks every one and runs every true one. An if / else if chain runs exactly one branch: the first true one, and then it is finished. Use a chain whenever the cases are meant to exclude each other.

The dangling else

Now the one that catches everybody. Read this and decide what it prints for a positive, odd number like 3:

What does this do with number = 3?
int number = 3;

if (number > 0)
    if (number % 2 == 0)
        System.out.println("even number");
else
    System.out.println("number is negative!");
Console
number is negative!

3 is positive. The program says it is negative.

The indentation lines the else up with the outer if, which is clearly what whoever wrote it meant. Java does not read indentation. Its rule is much simpler and completely unmoved by whitespace:

Rule

An else belongs to the nearest if above it that does not already have one. Nothing about how you indent it changes that.

The nearest if without an else is the inner one. So what Java compiled is this — the same characters, honestly indented:

What Java actually built
if (number > 0)
    if (number % 2 == 0)
        System.out.println("even number");
    else
        System.out.println("number is negative!");   // the ODD branch

Read that way, the message is exactly where it lands: 3 is positive, so we go inside; 3 is not even, so we take the else — which is the odd branch wearing the wrong label. And a genuinely negative number never gets inside the outer if at all, so it prints nothing.

numberWhat you expectWhat it actually prints
4even numbereven number
3nothingnumber is negative!
-3number is negative!nothing
0number is negative!nothing

Only the first row is right, which is exactly why the bug survives testing.

The fix is braces. Wrap the outer if and the inner one can no longer reach out and grab the else:

Braces close the inner if off
if (number > 0) {
    if (number % 2 == 0) {
        System.out.println("even number");
    }
}
else {
    System.out.println("number is negative!");
}
Console
number = 3  ->  (nothing)
number = -3 ->  number is negative!

If what you wanted all along was three separate answers, give the inner if its own else. Once the inner one is taken, the next else has no choice but to attach to the outer if:

Three answers, no braces needed
if (number > 0)
    if (number % 2 == 0)
        System.out.println("even number");
    else
        System.out.println("odd number");
else
    System.out.println("number is negative!");
Console
number = 4  ->  even number
number = 3  ->  odd number
number = -3 ->  number is negative!

This version is correct. It is also one deleted line away from being wrong again — which is the real argument for writing the braces every time.

Nested ifs and &&

An if inside an if, with no else anywhere, means “both of these must be true” — which is exactly what && from Lesson 1 says. These two print the same thing for every number:

Two ways to say both
if (number > 0) {
    if (number % 2 == 0) {
        System.out.println("positive even number");
    }
}

if (number > 0 && number % 2 == 0) {
    System.out.println("positive even number");
}

The second is shorter, and it has no inner if for a stray else to attach itself to. Nesting earns its place when each level needs its own else — like the three-answer version above.

History

The dangling else is older than Java. It was spotted in ALGOL 60, one of the first programming languages, around 1960, and language designers have dealt with it ever since. Java, C and C++ all use the same rule: the else goes to the nearest free if. Python took another way out — in Python, indentation is the structure, so the code means what it looks like.

In short

An if / else if / else chain runs exactly one branch: the first true one. Order the conditions so each branch can rely on the ones above it, and put the validity check first. Separate ifs are separate decisions. Test every boundary, one below and one above it. An else belongs to the nearest if without one — braces are the only way to say otherwise.
