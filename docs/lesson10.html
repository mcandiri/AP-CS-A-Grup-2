Static and References

Two questions this week, and they turn out to be about the same thing: where does a value live? Some values belong to every object separately, like a customer's balance. Some belong to the whole class at once, like the number of customers the bank has. Those are static. And when you write a = b with two Heights, no height is copied at all. Only an arrow is. That arrow is a reference, and once you can see it, a lot of strange things from earlier lessons suddenly make sense.

CupcakeMachine

A short class we wrote in class: a machine that sells cupcakes. It knows how many cakes it has, what one costs, and how many orders it has taken so far.

CupcakeMachine.java
public class CupcakeMachine {

    private int numCakes;
    private double price;
    private int orderNum;

    public CupcakeMachine(int c, double p) {
        numCakes = c;
        price = p;
    }

    public String takeOrder(int amount)
    {
        if (amount > numCakes) {
            return "Order cannot be filled";
        }
        double cost = amount * price;
        numCakes -= amount;
        orderNum++;
        return "Order number " + orderNum + ", cost $" + cost;
    }
}
  • The constructor takes two of the three fields. orderNum is not a parameter: a new machine has taken no orders, and the default 0 is exactly right.
  • takeOrder returns a String, it does not print one. Whoever called it decides what to do with the message: print it, show it on a screen, save it.
  • The early return. If there are not enough cakes, the method returns at once. Nothing below runs: no cost, no cakes taken, no order number used up.
  • The order of the last lines matters. orderNum++ comes before the String is built, so the first order is number 1, not 0.
CupcakeMachine k = new CupcakeMachine(6, 4.0);
System.out.println(k.takeOrder(4));
System.out.println(k.takeOrder(3));
System.out.println(k.takeOrder(2));
System.out.println(k.takeOrder(1));
Console
Order number 1, cost $16.0
Order cannot be filled
Order number 2, cost $8.0
Order cannot be filled

Six cakes. 4 are sold, 2 left. 3 is too many, refused, and the order number is not used up, so the next good order is number 2. Then 0 cakes are left, and even 1 is too many.

Watch out

Lesson 1 is back. With a price of 0.1, three cupcakes do not cost 0.3:

CupcakeMachine z = new CupcakeMachine(10, 0.1);
System.out.println(z.takeOrder(3));
Console
Order number 1, cost $0.30000000000000004

That is why real shops keep money in whole kuruş or cents, as an int, like the Product class in Lesson 9.

Keep this class in mind. Each machine counts its own orders. In the workshop we change one word, static, and the numbering becomes shared by every machine in the shop.

One number for the whole bank

Since Lesson 8, every field we have written belongs to one object. acc1 has its own balance, acc2 has its own. That is the whole point of objects: two customers, two separate balances.

Now the bank asks a new question: how many customers do we have? Where should that number live? It is not Selin's number, and it is not Ceyda's. Let us try the obvious thing first, an ordinary field that every constructor adds one to:

Now there is only one customersCount. Every constructor adds 1 to that same number, so after three accounts it is 3, and every object that looks at it sees 3.

What static means

A static field belongs to the class itself, not to any one object. There is exactly one copy of it, however many objects you make: zero, one or a million. Every object of the class can read it and change it, and they all see the same value.

An ordinary field (one without static) is called an instance variable, because every instance, every object, gets its own. That is the kind we have written since Lesson 8. A static field is also called a class variable.

In real life

Think of a classroom. Every student has their own notebook: what is written in Ece's notebook is not in Can's. That is an instance variable. The board at the front is one board for everybody: when the teacher writes the date on it, every student sees the same date, and if one student wipes it, it is gone for all of them. That is a static variable.

Rule

A field marked static has one copy for the whole class, shared by every object. A field without static has one copy per object. Ask: does this value describe one object, or the class as a whole?

Three static fields

Here are the new lines at the top of BankAccount.java:

BankAccount.java · the fields now
public class BankAccount {

    private static String bankName = "Garanti";
    private static int customersCount = 0;
    private static double totalFees = 0;
    private String firstName;
    private String lastName;

    private String password;
    private double balance;
  • bankName: every account is at the same bank. Storing "Garanti" in every single object would be a waste, and if the bank changed its name, every object would have to be changed one by one.
  • customersCount: how many accounts exist. Not a fact about one account, a fact about all of them.
  • totalFees: all the money the bank has earned from fees, from every account together.

Notice the = "Garanti" and = 0 right on the field line. A static field is set up once, when Java first loads the class, before any object exists. It is not reset when a new object is made. That is exactly what we want from a counter. (= 0 is optional, like for any field: the default for a number is already 0.)

The word order is private static int: first who may see it, then static, then the type. They are still private. Static is about how many copies; private is about who may touch it. The two are separate questions.

You have used static since Lesson 5

This is not new, only its name is. The top of Lesson30.java puts the two kinds side by side:

Lesson30.java · the first lines
// non static

String str = "abc";

str.length();

// static

Math.pow(2, 3);
  • str.length() is an instance method. Its answer depends on which String you ask: "abc" says 3, "hello" says 5. So you must ask a String object.
  • Math.pow(2, 3) is a static method. Its answer depends only on its arguments, 2 and 3. There is no “Math object” to ask. Nobody ever writes new Math(). Math is simply a box of useful static methods: pow, sqrt, abs, random.
  • Math.PI and Integer.MAX_VALUE from Lesson 5 are static fields: one value, written on the class name.

And look at every method header we wrote in Lessons 5 to 7:

public static void main(String[] args)
public static boolean isPrime(int number)
public static String randomWord(int length)

All static. Back then we wrote static because we had to, and now we can say why. main is where the program starts. At that moment no object exists yet, so Java can only call a method that needs no object: a static one. And a static main can only call other methods without an object if they are static too. Take the word away from isPrime and see:

isPrime without static

        System.out.println(isPrime(7));
    }
    public boolean isPrime(int number) {
        ...
    }
}

    System.out.println(isPrime(7));

A method without static needs an object in front of its dot, and main has none to give. That is the same rule as the next section, seen from the other side.

In short

Static field: one copy, belongs to the class, shared by all objects. Static method: called on the class name, needs no object. Instance field and instance method: one per object, called on an object. Math.pow, Math.PI and main were static all along.

What static code cannot see

The commented-out lines in BankAccount.java are the errors we got in class, kept as comments so we remember them. Here is the first one:

BankAccount.java · commented out at the bottom
// public static void someFunction() { // Cannot make a static reference to the non-static field balance
//     System.out.println(balance);
// }
Compiler · with the comments removed
error: non-static variable balance cannot be referenced from a static context
        System.out.println(balance);
                           ^

The comment holds Eclipse's wording; the box shows what javac says. Same error, two ways to say it. Why is it an error? Ask yourself: whose balance? A static method is called as BankAccount.someFunction(), with no object in front of the dot. There may be two accounts, or a hundred, or none at all. Java has no way to know which balance you mean, so it refuses.

The second error is in printCount:

printCount with the comment removed
public static void printCount() {
    System.out.println(this.customersCount);
}
Compiler
error: non-static variable this cannot be referenced from a static context
    System.out.println(this.customersCount);
                       ^

Eclipse says it shorter: Cannot use this in a static context. this means “the object in front of the dot”, and a static method has no object in front of its dot. There is no this to use. Note that the field is static, so customersCount on its own is fine; only the this. is wrong.

The same goes for calling an instance method. Suppose printCount also wanted to print the account:

public static void printCount() {
    System.out.println(customersCount);
    print();
}
Compiler
error: non-static method print() cannot be referenced from a static context
        print();
        ^

Print which account? Same question, same answer.

The other direction is no problem at all. An instance method may use static fields as much as it likes. The constructors do customersCount++, and the new fee method adds to totalFees. Every object knows where the one shared box is.

Rule

A static method has no this. It can use static fields and call static methods directly, but it cannot touch an instance field or call an instance method without an object to ask. Instance methods can use everything.

From outside the class

Lesson29.java has more commented-out lines, from outside the class this time:

Lesson29.java · commented out
// System.out.println(BankAccount.bankName); // The field BankAccount.bankName is not visible

// System.out.println(acc1.bankName); // The static field BankAccount.bankName should be accessed in a static way
//                                    // The field BankAccount.bankName is not visible

“Not visible.” bankName is private static. Static does not mean public: private still means “only code inside BankAccount”. That is exactly why the class has printBankName(): a public static method that hands the private value out in a controlled way, like a getter. javac words it as bankName has private access in BankAccount.

“Should be accessed in a static way.” Writing a static member on an object, acc1.bankName, is allowed by Java if the field is visible, but Eclipse warns you, and with good reason. It looks as if the bank name belongs to acc1. It does not. Here is a public static field to show how misleading that is:

A public static field, written on objects
public class Shop {
    public static String city = "Istanbul";
}

// in main:
Shop s1 = new Shop();
Shop s2 = new Shop();
s1.city = "Ankara";
System.out.println(s2.city);
System.out.println(Shop.city);
Console
Ankara
Ankara

The line reads like “change the city of s1”. What it does is change the one city of the whole class, so s2 moved to Ankara too. Write it as Shop.city = "Ankara"; and nobody is fooled.

Watch out

Always write static things on the class name: BankAccount.printCount(), Math.pow(2, 3). acc1.printCount() compiles too, and prints the same number, but the code then lies about whose number it is.

And the opposite mistake, an instance method on the class name, does not compile at all:

BankAccount.print();
BankAccount.deposit(100);
Compiler
error: non-static method print() cannot be referenced from a static context
error: non-static method deposit(double) cannot be referenced from a static context

Print whose account? Deposit into which one?

Watch out

Making balance static would compile perfectly, and it would be a disaster: every customer would share one balance. Selin deposits 100, and Ceyda's balance goes up by 100. Static is not an extra feature to sprinkle on. It changes what the field means.

History

The word comes from C, the language Java borrowed much of its look from. In C, a static variable is one that stays in the same place in memory for the whole run of the program, instead of being made and thrown away again. Java kept the word for things that exist once, for as long as the class does.

BankAccount, Round 2

Last week's BankAccount got more than a counter. The bank now takes a 5% fee on every move of money, and two customers can merge their accounts into one. Both features need static, and the second one is our first method that returns an object.

A fee on every move

BankAccount.java · fee
private void fee(double amount) {
    double f = amount * 0.05;
    totalFees += f;
    balance -= f;
}

Three lines, two kinds of field. balance -= f takes the fee from this account; totalFees += f adds it to the bank's one shared total. An instance method using both an instance field and a static field: allowed, as the table above says.

fee is private, a helper like simplify or generatePassword. It is called at the end of deposit, withdrawal and transfer:

BankAccount.java · deposit now
public void deposit(double amount)
{
    if (amount > 0) {
        balance += amount;
        fee(amount);
        System.out.println("Current balance: " + balance);
    }
    else {
        System.out.println("Amount must be positive!");
    }
}

The fee is taken before the balance is printed, so depositing 100 into an empty account prints Current balance: 95.0. In transfer, both sides pay:

BankAccount.java · inside transfer
balance -= amount;
other.balance += amount;
fee(amount);
other.fee(amount);

fee(amount) with nothing in front means this.fee(amount): the sender pays. other.fee(amount) makes the receiver pay too. A private method called on a different object: allowed, because the line is inside BankAccount, the same rule as other.balance.

In class we also tried to call fee from Lesson29.java, a hundred times, to see how rich the bank could get. That code is still there, commented out:

And that is the whole point of private. If fee were public, any code anywhere could charge any customer any amount, with no deposit and no withdrawal. Private means a fee can only happen as part of a real money move.

merge: a method that returns an object

BankAccount.java · merge and deleteAccount
public BankAccount merge(BankAccount other)
{
    String newName = firstName + "&" + other.firstName + "'s account";
    double newBalance = balance + other.balance;
    deleteAccount();
    other.deleteAccount();

    return new BankAccount(newName, newBalance);
}

private void deleteAccount() {
    balance = 0;
    firstName = "Deleted";
    lastName = "account";
    customersCount--;
}

Read the header first: public BankAccount merge(BankAccount other). The return type is BankAccount. Until now our methods returned an int, a double, a boolean or a String. A method can just as well return an object of a class we wrote ourselves, and here it returns a brand-new account.

  1. The new name is built from both first names: "Selin" + "&" + "Ceyda" + "'s account" → "Selin&Ceyda's account".
  2. The new balance is the two balances added.
  3. Both old accounts are emptied by the private helper deleteAccount(): balance 0, name “Deleted account”, and the customer count goes down by one. Once for this, once for other.
  4. A new account is made with new BankAccount(newName, newBalance), inside the class's own method. Its constructor runs as always: it splits the name, checks the balance, makes a password, and adds 1 to the count.

The constructor splits the new name at its first space. "Selin&Ceyda's account" has one space, before account:

indexOf(" ") → 13 · firstName "Selin&Ceyda's" · lastName "account"

print() glues them back with a space, so the customer's name shows as Selin&Ceyda's account. And the count: two deleted (−2), one new (+1). Three customers become two.

In real life

When two people open a joint account, a real bank does almost exactly this: the old accounts are closed (not erased from the records, just marked closed), the money moves to a new account with a new number, and the new account's card comes with a new PIN. That is deleteAccount(), newBalance, and the constructor's generatePassword().

Lost objects


        
What happened to the 3 ft 9 Height after a = b? It is still in memory, but no variable leads to it, and nothing can ever lead to it again: you cannot write an arrow to an object you cannot reach. For the program it is gone. Such an object is called garbage.


        
Java cleans up by itself. Every now and then, a part of Java called the garbage collector looks for objects that nothing points at and gives their memory back, so it can be used for new objects. You never have to do it yourself, and you cannot tell exactly when it happens.


        

          History
          
Automatic garbage collection was invented around 1959 by John McCarthy for his language Lisp. One of Java's selling points in 1995 was that it did the cleaning for you.

Shared Boxes and Arrows Everywhere

        


        
Static and references are not exam tricks. Every real program is full of both, and once you know them you start seeing them in the apps you use every day.


        
Static: one value for everyone

Notice two different uses. Some static fields are shared settings: a VAT rate or a dollar rate that every object must use, and that should be changed in one place, not in a thousand objects. Others are shared counters: a next order number or a player count that keeps track of all the objects together. And static methods like Math.sqrt are tools: they need nothing but their arguments.


        

          In real life
          
The number on your receipt at a café, “Order 247”, comes from a static counter. Every order object takes the current number and adds one to it. If each order had its own counter, every receipt would say “Order 1”, exactly like our first Account1 try.

Most of the time, sharing is what you want: a transfer must reach the real account, and a shared cart must really be shared. The famous reference bugs come from the opposite case: a programmer wants a separate copy, writes a = b, and then is surprised when a change “to the copy” also changes the original.


        

          In real life
          
A classic real bug: a calendar app copies last week's meeting to make this week's, then moves this week's meeting to Thursday, and last week's meeting moves to Thursday too. The “copy” was an alias. The fix is always the same: new, then copy the values.

Ticket · a static counter gives every object an ID


        

          
Ticket.java

          
public class Ticket {
    private static int nextId = 1001;
    private int id;
    private String movie;

    public Ticket(String movie) {
        this.movie = movie;
        id = nextId;
        nextId++;
    }

    public void print() {
        System.out.println("#" + id + " " + movie);
    }

    public static int sold() {
        return nextId - 1001;
    }
}

// in main:
System.out.println(Ticket.sold());
Ticket t1 = new Ticket("Dune");
Ticket t2 = new Ticket("Up");
Ticket t3 = new Ticket("Dune");
t1.print();
t2.print();
t3.print();
System.out.println(Ticket.sold());

          
Console
0
#1001 Dune
#1002 Up
#1003 Dune
3

        


        
This is the most common use of static in real programs. The static nextId is the shared counter; the instance id is each ticket's own number, copied from the counter at birth. Afterwards the counter moves on, but each ticket keeps the number it was given. Two Dune tickets, two different IDs. Student numbers, order numbers and account numbers are all made this way.


        
Converter · a class that is only a toolbox


        

          
Converter.java

          
public class Converter {
    public static double cToF(double c) {
        return c * 9 / 5 + 32;
    }
    public static double kmToMiles(double km) {
        return km * 0.621371;
    }
    public static int minutesToSeconds(int m) {
        return m * 60;
    }
}

// in main:
System.out.println(Converter.cToF(100));
System.out.println(Converter.cToF(-40));
System.out.println(Converter.cToF(36.6));
System.out.println(Converter.kmToMiles(42.195));

-40.0

26.218749345

No fields, no constructor, nothing to remember: every answer depends only on the argument. That is exactly what Math is, and why every method here is static. Nobody needs to write new Converter(); you just call Converter.cToF(…), like Math.sqrt(…). (−40 is the one temperature that is the same in both scales. And 36.6 is Lesson 1's floating-point surprise again.)


        
Player · a record that belongs to nobody


        

          
Player.java

          
public class Player {
    private static int record = 0;
    private static String recordHolder = "nobody";
    private String name;
    private int best;

    public Player(String name) {
        this.name = name;
    }

    public void addScore(int score) {
        if (score > best) {
            best = score;
        }
        if (score > record) {
            record = score;
            recordHolder = name;
            System.out.println("New record: " + name + " " + score);
        }
    }

    public void print() {
        System.out.println(name + " best " + best + " | record " + record + " by " + recordHolder);
    }

    public static void printRecord() {
        System.out.println("Record: " + record + " (" + recordHolder + ")");
    }
}

// in main:
Player.printRecord();
Player p1 = new Player("Ece");
Player p2 = new Player("Can");
p1.addScore(120);
p2.addScore(90);
p2.addScore(150);
p1.addScore(140);
p1.print();
p2.print();
Player.printRecord();

          
Console
Record: 0 (nobody)
New record: Ece 120
New record: Can 150
Ece best 140 | record 150 by Can
Can best 150 | record 150 by Can
Record: 150 (Can)

        


        
Two max-so-far accumulators from Lesson 3 side by side: best is each player's own (instance), record is the game's (static). Ece's 140 beats her own 120, so her best changes, but it does not beat the record, so the static fields stay with Can. addScore is an instance method that updates both kinds: allowed. printRecord uses only static fields, so it can be static.


        
The swap that doesn't swap


        
A classic AP question. This method is supposed to swap two Heights:


        

          
Two ways to "swap"

          
public static void swap(Height p, Height q) {
    Height t = p;
    p = q;
    q = t;
}

public static void swapValues(Height p, Height q) {
    int f = p.getFeet();
    int i = p.getInches();
    p.setFeet(q.getFeet());
    p.setInches(q.getInches());
    q.setFeet(f);
    q.setInches(i);
}

// in main:
Height a = new Height(5, 3);
Height b = new Height(6, 1);
swap(a, b);
a.printHeight();
b.printHeight();
swapValues(a, b);
a.printHeight();
b.printHeight();

          
Console
5 ft. 3 inc.
6 ft. 1 inc.
6 ft. 1 inc.
5 ft. 3 inc.

        


        
swap does nothing the caller can see. p and q are the method's own copies of the arrows. Swapping them swaps which object each copy points at, and then the method ends and the copies are thrown away. a and b were never touched. swapValues works because it follows the arrows and changes the objects. The same rule as replace and grow.


        

          In short
          
A static counter plus an instance ID gives every object a unique number. A class with only static methods is a toolbox, like Math. Static and instance fields can sit side by side, like a personal best and a game record. A method can change the objects it is given, but not the caller's variables.
