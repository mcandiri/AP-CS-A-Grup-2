Constructors

In this lesson

Born empty

Here is how we made a height last week:

Lesson 8 style
Height h1 = new Height();
h1.setFeet(6);
h1.setInches(9);
h1.printHeight();
Console
6 ft. 9 inc.

It works, but think about what it means. Between the first line and the third, h1 exists, but it is not really a height yet. It is 0 ft 0 in., a person with no height at all. If someone forgets the setter lines, nothing warns them. The object just stays like that. Last week's Student was worse: until setName was called, its name was null, and one call to getName().length() was enough to crash the program.

In real life, things are not made empty and filled in later. A baby gets its name on the birth certificate on day one. A new phone leaves the factory with a language, a time zone and a ringtone already set. A bank will not open an account until you give it your name. The object should be ready the moment it exists. That is what a constructor is for.

What is a constructor?

A constructor is a special block of code inside a class that runs automatically, exactly once, when an object is made with new. Its job is to give the new object's fields their first values, its starting state.

Three ideas in that sentence are worth reading again:

  • Automatically. You never call a constructor the way you call a method, as h1.something(). Writing new Height(…) is the call.
  • Exactly once. Each object goes through its constructor one time, at its birth, and never again. Every object made later goes through it again, for itself.
  • Its first values. A constructor sets things up. What happens to the object afterwards is the job of the other methods: setters, add, deposit…

Here are the three constructors we added to Height.java in class. The comments above each one show the new that uses it:

How to write one

The comment at the top says it in two words: // public classname. A constructor looks like a method, with two differences that matter a lot:

publicanyone may make one
    no return type, not even void
Heightexactly the class name, capital H
(int feet, int inc)what you must give at new
{ … }sets the fields

The empty box is the point: where a method has void or int, a constructor has nothing.

Rule

A constructor has the same name as the class, spelled the same way, and no return type, not even void. In AP code it is always public. It may have parameters, and a class may have several constructors.

Why no return type? Because a constructor does not hand anything back. new makes the object; the constructor only fills it in. The finished object is what new gives back, and that is always an object of this class, so there is nothing to declare.

What happens at new

Take the first line from the top of Lesson29.java: Height h1 = new Height(6, 19);. Java does four things, always in this order:

1 · make roomfeet 0 · inches 0every field gets its default value first
pick→(int, int)
2 + 3 · run the bodyfeet 6 · inches 19this.feet = feet; inches = inc;
simplify→
still inside the constructorfeet 7 · inches 719 / 12 = 1 more foot, 19 % 12 = 7
4→h1
h1gets the finished object

Step 2 is choosing which constructor to run (there are three). Nobody can use h1 before step 4, so nobody ever sees the 19.

  1. Make room. Java makes a new object with space for feet and inches. Every field starts with its default value, exactly as in Lesson 8: 0 for int, 0.0 for double, null for String.
  2. Pick the constructor whose parameters match the arguments: two ints → Height(int feet, int inc).
  3. Run its body, with feet = 6 and inc = 19. The body can call methods too: here it calls the private simplify().
  4. Hand back the object. Only now does h1 get it.

You can watch it happen. The one-int constructor prints "Hi", so we can see exactly when it runs:

The "Hi" appears on the new line, before "after", even though nobody called a method named Hi or anything else. That is what “automatically” means.

In short

At new: defaults first, then the constructor body, then the object goes to the variable. A field the constructor does not touch keeps its default.

Height(int feet, int inc)

Height.java
public Height(int feet, int inc)
{
    this.feet = feet;
    inches = inc;
    simplify();
}

Two lines, two styles, both right, and for the same reason as last week:

  • The first parameter is called feet, the same name as the field. Inside the constructor, plain feet means the parameter, so the field must be written this.feet. Here this is the brand-new object being built.
  • The second parameter is called inc, a different name, so inches can only mean the field. No this needed.

The last line is the important one. The class made a promise last week: inches are always 0 to 11. A constructor that took 19 inches and stopped there would break that promise on day one. So it calls simplify(), the same private helper the setters use. A private method can be called from a constructor like from any other code inside the class.

The order of the arguments is the order of the parameters, and Java does not guess. new Height(19, 6) is not the same height:

new Height(19, 6).printHeight();
Console
19 ft. 6 inc.

The first number goes into the first parameter, every time. Both are ints, so Java cannot notice the mistake for you.

More than one constructor

Height has three constructors, all called Height. How does Java know which one you mean? It looks at the arguments, how many there are and of what types, and picks the constructor whose parameter list matches. Writing several constructors with different parameter lists is called overloading.

In real life

A café sells the same coffee three ways. “A latte, large, oat milk” gets exactly that. “A latte” gets the café's usual size and milk. Just “a coffee” gets the house filter coffee. Same counter, different amounts of detail, and the barista knows which order it is by what you said. That is overloading.

The no-argument constructor

The third constructor takes nothing:

public Height() // no argument constructor --- default constructor
{
    feet = 99;
    inches = 11;
}

It is used when someone writes new Height() and gives no information at all. Then the class itself decides what a “fresh” height looks like. In class we picked 99 ft 11 in. on purpose, so that you can see this constructor run. With the defaults, a fresh Height would look like 0 ft 0 in. and you could not tell the difference. In a real program you would choose a sensible starting value, the way a new phone starts at a sensible volume, not at zero and not at maximum.

That choice has a visible effect on last week's code. new Height() now means 99 ft 11 in., so a setter that is refused, or never called, leaves those values in place:

Height g = new Height();
g.setFeet(5);
g.setInches(0);   // refused: setInches only takes values > 0
g.printHeight();
Console
5 ft. 11 inc.

The one Java writes for you

Wait. Last week Height had no constructor at all, and new Height() still worked. So did new Student(). How?

Because if a class has no constructor at all, Java quietly gives it one: public, no parameters, an empty body. It does nothing, so every field keeps its default value. Strictly, the name default constructor belongs to that invisible one. Many people, and our comment in the file, also call any no-argument constructor “default”. On the exam, what matters is the rule:

Rule

Java writes the free, empty constructor only when the class has no constructor at all. As soon as you write one constructor, any one, the free one is gone. If you still want new X() to work, you must write X() yourself, which is exactly what we did in Height.

Here is what happens without it. A small class with only a one-int constructor:

Box.java and a main that uses it
public class Box {
    private int w;
    public Box(int w) { this.w = w; }
}

// in main:
Box b = new Box();
Compiler
error: constructor Box in class Box cannot be applied to given types;
  required: int
  found:    no arguments

The compiler is saying: “the only way to make a Box is with one int, and you gave me nothing.” That is not always a mistake. Sometimes it is the whole idea. A bank account should not exist without a name, so a class can refuse new BankAccount() simply by not having a no-argument constructor.

History

Java did not invent the name or the idea. It took both from C++, where Bjarne Stroustrup had added constructors in the early 1980s, along with the rule that the constructor carries the class's name.

Constructor, setter, getter

Now the class has three kinds of code that all touch the fields, and they are easy to mix up. A constructor looks like a setter: it takes values and puts them into fields. The difference is when it runs and how many times.

All three in one piece of code:

Constructor, then getter, then setters
Height k = new Height(6, 9);       // constructor: born as 6 ft 9
System.out.println(k.getFeet());   // getter: only reads
k.setInches(15);                   // setter: changes inches later
k.printHeight();
k.setFeet(5);                      // setter: changes feet later
k.printHeight();
System.out.println(k.getFeet() + " " + k.getInches());
Console

7 ft. 3 inc.
5 ft. 3 inc.
5 3

Read it as a life story. The constructor is the birth: it happens once, and it is where the object gets everything it needs to start. The setters are the changes that come later: a new e-mail address, a new password, a few more inches. The getters are someone asking a question: they never change anything. You can call setFeet a hundred times. You can never call the constructor again on k; k.Height(5) does not even compile.

There is a second difference, and it is a sneaky one: the checks. setFeet refuses a value that is not above 0. The two-int constructor checks nothing:

The setter checks, the constructor does not
Height h = new Height(6, 9);
h.setFeet(-5);         // refused by the if in setFeet
h.printHeight();

Height g = new Height(-5, 3);   // nothing stops it
g.printHeight();
Console
6 ft. 9 inc.
-5 ft. 3 inc.
Watch out

A guard on the setter protects only the setter. If the constructor writes straight into the field, a bad value can still get in, through the front door, at birth. A class that checks its values must check them in the constructor too. The easiest way: let the constructor call the setter, so the check is written once. The Product class in the workshop does exactly that.

In short

Constructor: the first values, once, at new, no return type. Setter: a change, any time, any number of times, void. Getter: a look, any time, returns the value, changes nothing. Checks belong wherever a field gets written, and the constructor is one of those places.

Mistakes that compile, and ones that don't

1 · A return type. Add void in front, and it is no longer a constructor. It is an ordinary method that happens to be called Box. Java allows that, so the class still compiles. The error comes later, where you try to use it:

public class Box {
    private int w;
    public void Box(int w) { this.w = w; }   // a method, not a constructor!
}

// in main:
Box b = new Box(5);
Compiler
error: constructor Box in class Box cannot be applied to given types;
  required: no arguments
  found:    int

Read the message: required: no arguments. The class now has no constructor, so Java gave it the free empty one, and that one takes nothing.

2 · The same name, without this. This one compiles and runs, and gives the wrong answer:

Point.java
public class Point {
    private int x;
    private int y;

    public Point(int x, int y) {
        x = x;
        y = y;
    }

    public void print() {
        System.out.println("(" + x + ", " + y + ")");
    }
}

// in main:
Point p = new Point(3, 4);
p.print();
Console
(0, 0)

Exactly last week's inches = inches;, now in a constructor: both names mean the parameter, the fields keep their defaults. Fix: this.x = x; this.y = y;.

3 · Calling the constructor like a method.

Height h = new Height(6, 9);
h.Height(5);
Compiler
error: cannot find symbol
  symbol:   method Height(int)

A constructor is not a method of the object. It only runs at new.

4 · Arguments that match nothing. new Height(1, 2, 3) and new Height("6") both fail: the first because no constructor takes three ints, the second because "6" is a String, not an int.

BankAccount

Height's constructors only copy numbers into fields. A real constructor often has more work to do. The person opening an account says their name once, as one piece of text, and maybe gives a first deposit. From that, the account must work out a first name and a last name, check the money, and make a password nobody typed. All of that happens in the constructor, before the account is handed over.

The constructor receives "Selin Kavas" as one String. Lesson 6 has everything it needs: find the space, cut before it, cut after it.

fullName.indexOf(" ") → 5 · substring(0, 5) → "Selin" · substring(6) → "Kavas"
  • substring(0, index) stops before the space: "Selin".
  • substring(index + 1) starts after the space and runs to the end: "Kavas". Without the + 1 the last name would start with a space.
  • indexOf finds the first space. For "Ayşe Nur Kaya" the first name is "Ayşe" and the last name is everything after: "Nur Kaya".
  • No space at all → -1 → the name is refused.

Then the balance. The parameter is called balance, like the field, so the field is this.balance, last week's rule again, now inside a constructor. A balance that is not above 0 is simply not copied, and the field keeps its default, 0.0.

A password nobody typed

The last line of the constructor is password = generatePassword();. A constructor can call the class's private helper methods, and this one returns a String of four random digits:

BankAccount.java · generatePassword
private String generatePassword()
{
//  int p = (int)(Math.random() * 9000) + 1000;
//  return p + "";

    String numbers = "0123456789";  // 0897
    String pw = "";
    for (int i = 0; i < 4; i++) {
        int r = (int)(Math.random() * numbers.length());
        pw += numbers.substring(r, r + 1);
    }
    return pw;

}

This is Lesson 7's randomWord, with digits instead of letters: four times, pick a random index from 0 to 9 and add that one digit to the result.

The two commented-out lines are the first idea: a random number from 1000 to 9999, turned into a String. It works, but look at the comment next to numbers: // 0897. A four-digit PIN may start with 0. The number version can never make one, because 1000 is its smallest value, and the int 0897 is just 897. Building the password digit by digit, as a String, keeps the zero. That is why the password is a String field and not an int.

In real life

When a bank sends a new card, the PIN in the envelope was made by the bank, not by you. You change it later at an ATM. Here, generatePassword() in the constructor is the envelope; resetPassword is the ATM.

deposit and withdrawal

BankAccount.java
public void deposit(double amount)
{
    if (amount > 0) {
        balance += amount;
        System.out.println("Current balance: " + balance);
    }
    else {
        System.out.println("Amount must be positive!");
    }
}
public void withdrawal(double amount)
{
    if (amount > 0 && amount <= balance) {
        balance -= amount;
        System.out.println("Current balance: " + balance);
    }
    else {
        System.out.println("Invalid amount!");
    }
}

There is no setBalance. Nobody outside may just set a balance; money comes in and goes out, and every change is checked. deposit takes only positive amounts. withdrawal also checks that the money is really there: amount <= balance. Both conditions must be true, hence &&.

resetPassword

BankAccount.java
public void resetPassword(String p) {

    if (isValid(p)) {
        password = p;
    }
    else {
        System.out.println("Invalid Password");
    }
}
private boolean isValid(String p) {
    String numbers = "0123456789";
    if (p.length() != 4) {
        return false;
    }
    for (int i = 0; i < p.length(); i++) {
        if (numbers.indexOf(p.substring(i, i + 1)) == -1)
        {
            return false;
        }
    }
    return true;
}

This is a setter with a check, like setYear in Student. The check is long enough to get its own private method. isValid uses Lesson 7's trick: to ask “is this character a digit?”, look it up in a String of all the digits. If indexOf says -1, it is not one of them, and the answer is false at once. Only a password that survives all four checks reaches return true.

transfer

BankAccount.java
public void transfer(BankAccount other, double amount, String password)
{
    if (amount <= balance) {

        if (amount > 1000 && this.password.equals(password)) {
            balance -= amount;
            other.balance += amount;
        }
        if (amount > 1000 && !this.password.equals(password))
        {
            System.out.println("Incorrect password!");
        }
        if (amount <= 1000) {
            balance -= amount;
            other.balance += amount;
        }

    } else {
        System.out.println("Invalid amount!");

    }
}

The bank's rule: small transfers (up to 1000) go through without a password; larger ones need the right password. Two accounts are involved, the same picture as h1.addHeight(h2): this is the account in front of the dot, the one that pays; other is the one in the parentheses, the one that receives.

Two names to keep apart. The parameter is called password, the password the user typed. The field is also called password, the real one. So the real one is this.password, and the check is this.password.equals(password): is the real password equal to the typed one? And never == for Strings.

other.balance += amount; writes a private field of a different object. It compiles for the same reason other.feet did last week: the line is inside the BankAccount class, and private is about where the code is written.

Holes in the bank

A bank class is a good place to practise thinking like an attacker: what can I give this class that it does not expect? Every one of these runs without an error message from Java.

Watch out

A negative transfer steals money. transfer never checks that amount is positive. −500 is “not more than the balance” and “not over 1000”, so no password is needed:

Watch out

A refused name leaves null behind. The constructor prints “Invalid name”, but it cannot stop the object from being made. A constructor has no way to say “no”. The object exists anyway, with both names still null:

Watch out

Silence. A negative starting balance, new BankAccount("Ali Can", -50), becomes 0.0 without a word. And a transfer that works prints nothing at all. Only the failures talk. A user who sends money and sees an empty screen has no idea whether it happened.

In short

A constructor can do real work: cut a String, check a value, call a private helper, before anyone gets the object. Two constructors give two ways to be born; no no-argument constructor means no account without a name. A constructor cannot refuse to make the object, so a bad argument leaves fields at their defaults. Every method that moves money needs every check, including amount > 0.

AP exam · 2019 free-response, question 2

StepTracker

Everything so far, fields, a constructor, methods that change the object and methods that only report, comes together in one of the classic AP exam questions. We solved it in class. Here it is again, slowly, with every decision explained.

What an FRQ is

The AP CS A exam has two halves. The first is multiple choice. The second is free response: a few questions where you write real Java code by hand, with no computer and no compiler to warn you. These are the FRQs, free-response questions.

One of them is always a class-writing question. You get a description of what a class should do, sometimes with a table of example calls, and you write the whole class: the header, the private fields, the constructor, every method. The fields are not given to you. Choosing them is part of the question. StepTracker, from 2019, is a perfect example: short, and every point in it is about a decision.

The question

Problem

A fitness tracker counts how many steps a person takes each day. Write a class StepTracker that keeps track of these days.

  • Its constructor takes one int: the minimum number of steps a day needs to count as an active day.
  • addDailySteps(int steps) records the steps of one more day.
  • activeDays() returns how many of the recorded days were active, that is, had at least the minimum.
  • averageSteps() returns the average number of steps per day as a double. If no day has been recorded yet, it returns 0.0.

The question shows the class at work with a table like this one. Read it as a test you have to pass:

Remember less

The first idea most people have: keep every day. Day 1 was 9000, day 2 was 5000… But how? We have no way to store a list of numbers whose length we do not know. And here is the good news: we do not need to.

Ask the class's two questions from Lesson 8, but about what the methods will need:

  • activeDays() needs how many days were active. Not which ones. One counter.
  • averageSteps() needs the total of all steps and how many days there were. Average = total ÷ days. Two more numbers.
  • To decide whether a new day is active, addDailySteps needs the minimum. It is given once, to the constructor, so it must be kept in a field.

After three days. The class never needs to know that day 2 was 5000. It only needs the running totals: the accumulators from Lesson 3.

This is the same idea as the accumulator loops from Lesson 3, where sum += i never remembered the earlier values of i, only their total. The difference: the “loop” is now spread over many method calls, so the accumulators must live in fields, which last as long as the object, not in local variables, which disappear at the end of each call.

Rule

Before writing a class, list what each method will need to know to give its answer. Whatever must be remembered from one call to the next becomes a private field. Keep the smallest set that works.

Solving it, step by step

Step 1 · The header and the fields. The class is public; every field is private. That is the first thing graders look for.

public class StepTracker {
    private int minSteps;
    private int totalSteps;
    private int days;
    private int activeCount;

Why activeCount and not activeDays? Java would allow a field and a method with the same name, but reading return activeDays; inside activeDays() is confusing. A different name keeps it clear.

Step 2 · The constructor. The question says it takes one int, the minimum. The parameter has the same name as the field, so: this.

    public StepTracker(int minSteps) {
        this.minSteps = minSteps;
    }

What about the other three fields? They must start at 0, and step 1 of new already did that. You may write totalSteps = 0; and so on. It is a good habit on the exam, since it shows the grader that you thought about it. It is not required.

Step 3 · addDailySteps. One more day has arrived. What changes? The total grows by steps, the day count by one, and, only if the day was active, the active counter by one.

    public void addDailySteps(int steps) {
        totalSteps += steps;
        days++;
        if (steps >= minSteps) {
            activeCount++;
        }
    }

Notice >=. The question says at least the minimum. A day of exactly 10000 is active. Writing > is a classic mistake on this question, and it costs points.

Step 4 · activeDays. All the counting already happened in addDailySteps. This method only reports, like a getter:

    public int activeDays() {
        return activeCount;
    }

Step 5 · averageSteps. Two traps, both from earlier lessons. First, no days: dividing by days when it is 0 must not happen, so that case returns 0.0 before any division. Second, totalSteps and days are both int, and Lesson 1 warned us what int / int does. Cast before dividing:

    public double averageSteps() {
        if (days == 0) {
            return 0.0;
        }
        return (double) totalSteps / days;
    }
}

The whole class

StepTracker.java
public class StepTracker {
    private int minSteps;
    private int totalSteps;
    private int days;
    private int activeCount;

    public StepTracker(int minSteps) {
        this.minSteps = minSteps;
    }

    public void addDailySteps(int steps) {
        totalSteps += steps;
        days++;
        if (steps >= minSteps) {
            activeCount++;
        }
    }

    public int activeDays() {
        return activeCount;
    }

    public double averageSteps() {
        if (days == 0) {
            return 0.0;
        }
        return (double) totalSteps / days;
    }
}

Three wrong averages

The last method is where most of the lost points are. With the numbers from the end of the table, totalSteps = 51111 and days = 5:

Four ways to write the division
System.out.println(totalSteps / days);
double a = totalSteps / days;
System.out.println(a);
System.out.println((double) (totalSteps / days));
System.out.println((double) totalSteps / days);
Console

10222.0
10222.2
  • Wrong 1, totalSteps / days: int / int throws the .2 away. Returned from a double method, Java quietly widens 10222 to 10222.0, so it compiles and is still wrong.
  • Wrong 2, storing in a double: too late. The division already happened in int.
  • Wrong 3, (double) (totalSteps / days): the parentheses make Java divide first and cast afterwards. Lesson 1's (double)(x / y) trap.
  • Right, (double) totalSteps / days: the cast happens first, so it is double / int, a real division.

And the zero check? Without it, a brand-new tracker does this:

int total = 0;
int days = 0;
System.out.println((double) total / days);
System.out.println(total / days);
Console

With the cast, 0.0 / 0 is NaN, “not a number”, not the 0.0 the question asks for. Without the cast, it is Lesson 1's crash. The if (days == 0) must come before the division.

On the exam

Graders mark a class-writing question piece by piece. Most of the points are for things that look small:

  • The header, public class StepTracker, and every method header exactly as described: same name, same parameter type, same return type. averageSteps returns double, activeDays returns int.
  • Private fields, all of them. One public field can cost a point.
  • The constructor saves its parameter in a field. A constructor that does nothing with the minimum makes addDailySteps impossible to write correctly.
  • Return, don't print. activeDays() must return the number. System.out.println(activeCount); in its place is wrong, even though it shows the right number on the screen.
  • The details: >=, the cast, the zero check.
In short

A class-writing FRQ is “has, is born with, can do” on paper. Choose fields by asking what each method needs to know; usually a few running totals are enough. The constructor stores what it is given; the other fields start at 0. Methods that change the object do the work; methods that report just return. Cast before dividing, and check for zero before that.

Where Constructors Live

Every app makes objects all day long, and every one of them goes through a constructor. A useful way to see it: what must you give to get one? Whatever you must give becomes a constructor parameter. Whatever can be changed later becomes a setter.

public class Clock {
    private int hours;

    public Clock(int h, int m) {
        hours = h;
        minutes = m;

        simplify();

    private void simplify() {
        hours += minutes / 60;

        hours = hours % 24;
