Passed by Value

You call a method and hand it a variable. When the method is finished, is your variable still the same? For an int the answer is always yes. For a Height the answer is “it depends”, and it depends on one thing only: did the method change the object, or did it only move its own arrow? This is one of the most asked questions on the AP exam, so this lesson takes it slowly, one picture at a time, and ends with a checklist you can use on any question.

In this lesson

  • Why increment(number) cannot change number, and why increment(h) can change h's object.

In Lesson 5 we learned that a parameter is a copy. In Lesson 10 we learned that a variable like Height h does not hold a Height, only an arrow to one. Put those two facts together and you get the whole of this lesson. It sounds small, but it is the reason behind a large share of the “what is printed?” questions on the exam, and most mistakes come from knowing the two facts separately but not together.

What happens at a call

When Java reaches the line increment(number);, four things happen, always in this order:

  1. The argument is worked out. number is 9, so the value going in is 9. (If you write increment(2 + 3), the value is 5. If you write increment(5), it is 5.)
  2. The method gets fresh variables of its own. Every parameter is a brand-new variable that exists only while the method runs. Java sets aside a little area of memory for the call, called a frame, and puts the parameters there.
  3. The value is copied into the parameter. This is exactly the line from the comment in the file: number = a;. It is an ordinary =, the same = as in x = y.
  4. The body runs. When it ends, the frame is thrown away, with all the parameters and local variables in it. Java goes back to the line after the call.
Rule

At every call, Java copies the value of each argument into a new parameter variable. This is called passing by value, and it is the only way Java ever passes anything. What changes from type to type is only what the value is: a number for an int, an arrow for an object.

increment(int): a copy of the number

Now the first three lines of output are easy:

  • Before method: 9. Nothing has happened yet.
  • In method: 10. The method's own number started as a copy of 9, and number++ made it 10.
  • After method: 9. The frame with the 10 in it is gone. main's number was never touched.

It does not help that both variables are called number. A parameter's name is just the name inside the method. It is the same scope rule from Lessons 3 and 5: a variable lives in its own block, and two blocks can each have a variable with the same name without knowing about each other. The comment in the file uses a for the caller's variable on purpose, to make that clear: number = a; then number++;, so what happens to a? Nothing.

The next lines in main are the same idea without a method:

x = y copies 3 into x, and then the two have nothing to do with each other: y++ does not reach x. A call does exactly this, with the parameter on the left and the argument on the right.

And then the strongest proof of all, increment(5);, which prints In method: 6. If the method could change the caller's variable, what would it change here? The number 5 itself? There is no variable to change. The method receives a value, not a variable, so passing a literal works exactly like passing a variable.

Watch out

Printing inside the method is what fools people. In method: 10 is true; it is just about a different variable. When a question asks what is printed after the call, look at the caller's variable, not the method's.

Two methods called increment

Lesson31 has increment(int number) and increment(Height ht). Two methods with the same name in one class: that is allowed, as long as their parameter lists are different. It is the same thing we did with Height's three constructors in Lesson 9. It is called overloading.

Java chooses which one to run by looking at the arguments:

increment(Height): a copy of the arrow

Now the same rule with a Height. h holds an arrow to a Height object, so the value that is copied is the arrow. This is the comment in the file again: ht = h;. After that line, ht and h are aliases, two arrows to the same object, exactly like a = b in Lesson 10.

Rule

When an object is passed to a method, the parameter gets a copy of the reference, never a copy of the object. Through that copy the method can reach the caller's object and change it, and the change is still there after the method ends.

What is copied for an object: the reference

Above increment(Height ht) we wrote Passed by reference, and that is the name many people use for this case: the method can reach the caller's object. You will hear it a lot. But look at what Java really did: it copied something, exactly as with the int. Only this time the thing in the variable, and so the thing copied, was a reference. The object itself was not copied, not even partly.

Rule

Java always passes by value. For a primitive, the value copied is the number. For an object, the value copied is the reference: the parameter becomes one more arrow to the very same object. This is the sentence the AP exam is built on.

In real life

A hotel gives you a key card for room 304. If you ask for a second card for your friend, the hotel does not build a second room 304: it makes a second card for the same room. That card is a copied reference. Your friend can go in and move the furniture (change the object). But if reception re-codes your friend's card for room 512, your card still opens 304 (reassigning the parameter).

Why does the difference matter? Because if the method really had the caller's variable, it could also make that variable point somewhere else. It cannot. That is exactly what increment2 shows.

increment2: the new arrow

Rule

Assigning to a parameter (ht = …) changes only the method's own copy. A method can change the caller's object, but it can never change what the caller's variable points at.

Watch out

In a question, the line to look for is parameter = new … or parameter = something else. From that line on, everything the method does through that parameter happens to a different object, and the caller never sees it.

Making increment2 work

There are two honest ways to get a taller h out of a method.

1 · Change the object. Follow the arrow and use a method that changes the fields. That is increment(Height ht) with its ht.add(1). It works because add changes the object itself.

2 · Return the new object, and let the caller catch it. The method cannot move the caller's arrow, but the caller can, with its own =. This is what merge did in Lesson 10.

Return the new Height
public static Height increment3(Height ht) {
    return new Height(ht.getFeet(), ht.getInches() + 1);
}

// in main, h is 4 ft. 3 inc. here
increment3(h);
h.printHeight();

h = increment3(h);
h.printHeight();
Console
4 ft. 3 inc.
4 ft. 4 inc.

The first call builds a 4 ft 4 and hands its arrow back, but nobody catches it: it is garbage at once. The second call is caught by h = , so now h points at the new object. Notice the difference from way 1: here the old 4 ft 3 object was never changed; h simply points at a different one. If another variable was an alias of the old object, it would still see 4 ft 3.

In short

A method gets copies. A copy of a number cannot reach anything. A copy of an arrow can reach the caller's object, so changes made through it stay. Pointing the copy at something new (ht = new …) is invisible to the caller. To give the caller a new object, return it and let the caller assign it.

Watch out

If you see ClassName@ and some letters and digits in your console, you printed the reference, not the object's values. It is not an error and nothing crashed. Call the class's own print method, or give the class a toString (next section).

toString: teaching Java to print a Height

In Height.java as it is now, one method is commented out. In class we wrote it to fix exactly this problem:

Height.java · toString
// toString --> string representation ....
public String toString() {
    return this.feet + " ft. " + inches + " inc.";
}

toString is a special name. Whenever Java needs an object as text, it looks for a method with exactly this header, public String toString(), and calls it by itself. You almost never write h.toString(): println and + with a String do it for you. With the comment marks taken away:

With toString in Height
Height h = new Height(4, 3);
System.out.println(h);
System.out.println("Height: " + h);
String s = h.toString();
System.out.println(s.length());
h.add(10);
System.out.println(h);
Console
4 ft. 3 inc.
Height: 4 ft. 3 inc.
12
5 ft. 1 inc.
  • println(h) calls h.toString() and prints the String it returns, instead of Grup1.Height@….
  • "Height: " + h is String + object: Java turns the object into text with toString, then joins.
  • The result is an ordinary String, 12 letters long. We can store it and use String methods on it.
  • It always shows the object as it is now: after add(10), 5 ft 1.

toString or printHeight? Both show the height, but in different ways. printHeight is void: it prints, and gives nothing back. toString returns a String and prints nothing itself. Returning is more useful: the caller decides what to do with the text: print it, join it to other text, store it, count its letters. It is also an accessor: it only looks at the fields and changes nothing.

Rule

The header must be exactly public String toString(): public, returns a String, no parameters. It must return the text, not print it.

Watch out

Spell it exactly. A method called tostring() or ToString() compiles without a word, but it is just another method: println does not know it and still prints ClassName@…. And a toString that prints instead of returning will not compile: missing return statement.

In real life

Every app shows objects as text all the time: a contact as “Ayşe · 0555 …”, an order as “#247 · 3 items · 300 TL”, a match as “Kartallar 2–1 Aslanlar”. Each of those is somebody's toString: the one place in the class that decides what the object looks like when written down.

After the Call, What Changed?

        


        
On the exam, the question almost never says “passed by value”. It shows you a class, a method and a few lines of main, and asks what is printed. Behind it there is always the same question: did this call change the thing I am printing? This part goes through every case you will meet, one by one, and ends with a checklist that answers it.

Strings behave like ints


        
A String is an object, so a String parameter gets a copy of an arrow, like a Height. Then why is it in the “No” row? Because of something we saw in Lesson 6: a String never changes. There is no add, no setter, no method that changes the letters of a String. Every String method that seems to change it, like substring, or +, builds a new String. So the only thing a method can do with its String parameter is the increment2 move: point its own copy at a new String.

What a getter gives you


        
increment2 starts with int ft = ht.getFeet();. What does ft hold? A copy of the number. A getter returns a value, and returning works just like passing: the value is copied. So ft is an ordinary int with no connection to the object.

Returned values must be caught


        
A method that returns a value does not change anything by returning it. If you call it and do nothing with the result, the result is lost, like the first increment3(h) and the first city.substring(0, 3) above. The same happens with Math:

          Watch out
          
Java lets you call a method and ignore what it returns: Math.abs(x); and city.substring(0, 3); compile without a warning. But a bare calculation is not a statement at all: x + 1; or h.getFeet() + 1; will not compile (not a statement).

        


        
Which objects can a method change?


        
So far all our methods were static, with the object as a parameter. But most methods we write in a class are instance methods: h.add(1), acc1.transfer(acc2, 200, "1905"). There is a hidden extra arrow in those: this, the object before the dot. When you call h.add(1), this inside add is a copy of h's arrow. Everything in this lesson applies to it too.


        
So an instance method can change, at most:


        
    
          
  1. this: the object before the dot, through its fields (inches += inc is this.inches += inc).
    2. 
          
  2. any object passed as a parameter, through that parameter's arrow (other.balance += amount).
    3. 
          
  3. static fields of the class (customersCount--, totalFees += f).
    4. 
        


        
It can never change the caller's primitive variables, the caller's Strings, or what any of the caller's variables point at. Here is that list for every method we have written:

          Watch out
          
private does not protect the parameter's object from the class's own methods. transfer writes other.balance although balance is private: private means “only code inside BankAccount”, and transfer is inside BankAccount. It does not mean “only this object”.

        


        
Two names for one parameter


        
What if the caller passes the same object twice, or passes an object to its own method? Then two arrows inside the method lead to one object, and every change through one is seen through the other. Lesson 10 met this with a.merge(a). With Height:


        

          
A Height added to itself

s.addHeight(s);

this and other are both copies of s's arrow. this.feet += other.feet is 5 + 5 = 10. Then inches += other.inches: other.inches is this.inches, still 3, so 3 + 3 = 6. The height is doubled. The danger is when a line reads a field that an earlier line has already changed through the other name: then it reads the new value, not the old one. With an alias you cannot think of this and other as two separate objects; trace them as one.


        
Static doesn't decide


        
Notice that Lesson31's three methods are all static, and one of them changes an object anyway. Being static only means there is no this. It does not protect objects passed in. And an instance method is not more “powerful” with its parameters than a static one. What decides whether something changes is always the same: does the code follow an arrow to an object and change a field there?


        
The checklist


        

        
In words, for each variable the question asks about:


        
    
          
  1. Find its type. int, double, boolean or String: the call did not change it. Stop.
    2. 
          
  2. It is another object. Draw the arrows: the caller's variable, the parameter, and this if there is a dot.
    3. 
          
  3. Walk through the method line by line. Every time a line calls a mutator or writes a field through an arrow, change the object it leads to.
    4. 
          
  4. When a parameter is assigned (p = …), move only that parameter's arrow.
    5. 
          
  5. At the end, erase the method's frame. Read the answer by following the caller's arrows, which have not moved.
    6. 
          
  6. Was something returned? It counts only if the caller caught it with =.
    7. 
        


        

          In short
          
Primitives and Strings: never changed by a call. Objects: changed only through an arrow, before any new arrow. Getters give copies. Returned values must be caught. An instance method can change this, the objects it is given, and static fields, nothing else. private and static do not change any of this.

Classes from Real Life

        


        
Height and BankAccount are not the only classes in the world. The same rule works for every class anyone ever writes: a number goes in as a copy of the number, an object goes in as a copy of its reference.     private int battery;

A garage remote is a reference to the garage door. Giving your neighbour a second remote (copying the reference) lets them open your door. If they re-pair their remote with their own garage (reassigning the parameter), your door is not affected and your own remote still works. What they can never do with their remote is change which door your remote opens.

        


        
The same idea protects real programs. When a banking app passes your balance as a number to a method that works out interest, that method cannot accidentally change your balance, because it only has a copy. When it passes your account object to a method, that method can change the account, and programmers know to read such a method carefully. That is why methods that only look (accessors) and methods that change (mutators) are kept apart and named clearly: getBalance promises to look, withdraw warns you that it changes.


        

          History
          
Early languages chose differently. FORTRAN, from the 1950s, usually passed the caller's variables themselves, so a subroutine could change them; there are famous stories of programs where a subroutine changed what was passed in as a constant like 1, and from then on “1” meant something else. ALGOL 60 (1960) let the programmer choose for each parameter: a copy of the value (call by value) or something closer to the caller's own expression (call by name). C passes everything by value. Java, designed in the 1990s, chose the simplest rule of all: always by value, with references as the values for objects. One rule, no exceptions.

1 · A number and an object in one call.


        

          
mystery

          
public static void mystery(int n, Wallet w) {
    n += 10;
    w.add(n);
    w = new Wallet(0);
    w.add(100);
}

30

        


        
In the second call from and to are two copies of a's arrow. 20 goes out and the same 20 comes back in.


        
3 · A method that returns a new object.


        

          
richer

          
public static Wallet richer(Wallet w) {
    Wallet r = new Wallet(w.getMoney() + 100);
    return r;
}

acc.withdrawal(rent) is a mutator called through the caller's arrow: Selin's real account loses 1000 and the 5% fee. rent = 0 changes only the method's copy of the number.


        
5 · A loop inside the method.


        

          
grow

          
public static void grow(Height h, int times) {
    for (int i = 0; i < times; i++) {
        h.add(times);
    }
    times = 0;
}

// in main:

h.printHeight();
System.out.println(t);

          
Console
5 ft. 9 inc.
3

        


        
Three times add(3): 9 inches, into the caller's object. t stays 3.


        
6 · Aliases and Lesson31's methods.


        

          
with increment and increment2 from Lesson31 (and the print inside increment2)

          
Height a = new Height(5, 0);
Height b = a;
increment2(b);

a.printHeight();

The two lines are the same, but they come from different places. The first is printed inside increment2, about its garbage object. The second is a, which changed through its alias b in increment(b).


        

          In short
          
Trace numbers and objects separately. Watch for the line that moves a parameter. When two parameters can be the same object, check that case. A returned object is only kept if it is caught. And a line printed inside a method is not the caller's variable.
