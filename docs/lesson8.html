Too many variables

The file starts with something we already know how to do — one variable for every piece of information:

The first lines of Lesson27.java
String name = "mehmet can";
int age = 34;

String name2 = "ali";
int age2 = 17;

Two people, four variables. Now imagine the whole class: 20 students, and for each one a name, a birth year, a school e-mail and an average. That is 80 variables — name17, email17, average17… Nothing in Java says that name17 and average17 belong to the same person. If you mix up one number, Selin gets Rüzgar's average.

What we want is one thing called a student that carries all four pieces with it. Java lets us invent that thing ourselves. It is called a class.

What is a class?

Every value we have used so far had a type that Java gave us. int holds a whole number, double a decimal number, boolean true or false, String a piece of text. Each of these holds one kind of thing.

But the things our programs are about are bigger than one number or one word. A student is not a number. A student is a name and a birth year and an e-mail and an average, all at the same time. Java has no type for that — so we write one. A class is a new type that you describe yourself. You describe it once, and from then on Java knows a Student as well as it knows an int.

Describing a class means answering two questions about that kind of thing:

  • What does it have? Its data. A student has a name, a birth year, an e-mail and an average. In Java, these become the class's instance variables.
  • What can it do? Its behaviour. A student can work out its age, print its information, and change its e-mail. In Java, these become the class's methods.

“Has” and “can do” are the two halves of every class you will ever read or write. When you meet a new class, ask both questions first:

Look at the last row. String has been a class all along — the people who made Java wrote it, and since Lesson 6 we have been using its methods. This week we stop only using classes and start writing them.

What is an object?

An object is one real thing made from a class. If Student is the idea of a student, an object is Selin. Three things are true of every object:

  • It has its own values. Selin's average is 91.5 and Rüzgar's is 78.0. Both have an average, because the class says so — but each fills it in for itself. The values an object holds right now are called its state.
  • It can do what its class says. If the class has a method that works out the age, every student object can work out its own age, from its own birth year.
  • It is a separate thing. Two students who are both called Ali, born in the same year, with the same average, are still two students. Change one, and the other does not change.

Notice what happens when. The class is written once, before the program runs — it is text in a file. The objects are made while the program runs, as many as it needs: one for a single student, thirty for a whole class, a thousand for a whole school, all from the same few lines of Student.java.

The four pieces every student has — name, birthYear, email, average — are called instance variables. The comment in Student.java gives the other names you will hear for exactly the same thing: fields and properties. An object is also called an instance of its class: stu1 is an instance of Student.

What classes are for

We could keep writing programs with loose variables, as we have for seven lessons. So why do programmers bother? Four reasons, and you will see every one of them in this lesson.

1 · What belongs together stays together

With a class, Selin's name, birth year, e-mail and average travel as one thing. You cannot accidentally give her someone else's average, because her average is not a separate variable floating around — it is inside her object.

2 · The code speaks the language of the problem

A program for a school should be about students, teachers and lessons — not about name17 and average17. With a class, the code is written in those words: a Student, its name, its average. Later in this lesson a student will even work out its own age, and the line that asks for it reads almost like English: “student one, calculate your age.”

3 · Write once, use many times

Student.java is written once. Then every program that needs students — a grade book, a library, a bus list — can use it, for as many students as it likes. You use String every day without ever having seen the code inside it; that is this reason at work.

4 · The class can protect its own data

A class can refuse bad values — no birth year of −1234, no average of 250. This is the second half of the lesson: encapsulation.

Thinking in objects

Writing classes changes how you look at a problem. Before writing any code, you ask: what are the things in this problem? Take a school:

ClassHasCan do
Studentname, number, birth year, averagework out its age, print a report card
Teachername, branch, e-mailenter a grade
Classroomname (“11-A”), floor, number of seatstell if it is full
Lessonsubject, day, hour, teacherprint the timetable line

A handy trick: read the problem and underline the nouns — student, teacher, classroom, grade. The important nouns become classes, and smaller nouns that describe them (name, floor, grade) become their instance variables. Then underline the verbs — enter, print, calculate. They become methods. This way of building programs out of objects is called object-oriented programming, and Java is built for it from the ground up.

History

Classes and objects were invented in Norway. In the 1960s Ole-Johan Dahl and Kristen Nygaard were writing programs to simulate real systems — ships, queues, factories — and found it natural to describe each kind of thing once and then make as many of them as they needed. Their language, Simula 67, was the first with classes and objects. In the 1970s Alan Kay and his team at Xerox PARC built Smalltalk on the same idea and gave it the name object-oriented programming. Java, in 1995, brought it to millions of programmers; today almost every large program is written this way.

Age 2026! 2026 - stu1.birthYear uses a birth year that is still its default, 0. The program does not crash — it quietly gives a wrong answer. A default value is not a real value; it only means “nobody set this yet”.

And remember Lesson 7: a String field starts as null, not "". Printing it shows the word null; calling a method on it crashes.

Every object has its own

new builds a new object every time. Two students are two separate sets of four boxes:

stu1Student

Two students, two separate objects. Changing stu1’s name never touches stu2’s name — they are different boxes that happen to have the same label.

That is why the field is called an instance variable: there is one copy per instance. Twenty students, twenty names — but you wrote String name; only once.

In short

A class is a type you write yourself: it says what every object of that kind has (instance variables) and what it can do (methods). An object is one real thing built from the class with new; it has its own values and lives separately from every other object. Fields that nobody has set hold their default: null, 0, 0.0, false.

private, Encapsulation, Getters & Setters

In the first half we built objects. In this half we protect them. An object is only useful if its values make sense: a student with an empty name or a negative average is worse than no student, because the program will go on calculating with nonsense and print it as if it were true. The question of this part is: who is allowed to change an object's data, and who checks that the new value makes sense? Java's answer has three parts — private, setters and getters — and together they are called encapsulation.

Open fields: anyone writes anything

With the first version — nothing in front of the fields — look at what the second student got in class:

An empty name, a student born 1234 years before year zero, an e-mail with no @ and a negative average. Java accepted every line, and the student is 3260 years old. The Student class had no way to say no.

In class we first tried to fix it in main:

Checking from outside
stu2.birthYear = -1234;
if (stu2.birthYear < 0) {
    System.out.println("Invalid birth year!");
}

Two problems. The check runs after the bad value is already inside the object. And the check is in main, not in Student — every program that ever uses Student has to remember to write it again, every time it sets a birth year. Forget once, and −1234 is in.

Rule

Instance variables are private. Always. On the AP exam, a class you write with public instance variables loses points — no matter how good the rest is.

Encapsulation

But now the fields are locked away completely. How does anybody set a name? Through the class's own methods, which are public. The data is hidden inside; the methods are the only doors; and every door can check what comes through it. That idea is called encapsulation — wrapping the data up like the medicine inside a capsule.

Think about what changes. Before, the user of the class was responsible for every check: every program, every time. Now the class is responsible for its own data. The check is written once, in one place, and nobody can go around it. If the rule changes — say the school decides averages go up to 110 — you change one line in Student.java, and every program that uses it follows the new rule.

In real life

An ATM. Your balance is inside the bank's computer, and nobody can walk in and change the number. The machine is the only door: it lets you withdraw — but first it checks your PIN, then checks you have enough money. The bank never trusts the customer to check by themselves; the check is built into the door. That is exactly what moving the if from main into Student does.

Here are all four setters from the file. Each one has the same shape: public void, the name set…, one parameter of the field's type, and an if that guards the field.

    }

    } else {

    }

So why have a getter at all? Why not make the field public for reading? Because Java's private is all or nothing: a public field can be read and written. Methods that use the fields

A class is not only getters and setters. Any method in the class can use the object's fields directly — no parameters needed, because the object already knows its own data:

Student.java
public int calculateAge() {
    return 2026 - birthYear;
}

public void printStudentInfos() {
    System.out.println("*****STUDENT INFOS=====");
    System.out.println("Student's name: " + name);
    System.out.println("Student's age: " + calculateAge());
    System.out.println("Student's mail: " + email);
    System.out.println("Student's average: " + average);
}
  • calculateAge uses birthYear without a dot in front. Inside the class, birthYear means this object’s birth year: stu1.calculateAge() uses stu1’s, stu2.calculateAge() uses stu2’s.
  • The age is not stored. There is no age field — the age is worked out from the birth year each time it is needed. Store the birth year, which never changes; calculate the age, which changes every year. Compare the first lines of the file: int age = 34; will be wrong next year.
  • printStudentInfos calls another method of the same class, calculateAge(), also without a dot. Inside the class, it is understood: on this same object.

          In short
          
Encapsulation means the data of an object is private, and the only way in or out is through public methods. A setter (mutator) changes a field, but only after its if agrees the value makes sense; a rejected value changes nothing. A getter (accessor) hands back a field's value. A field with a getter and no setter is read-only. Methods without static belong to an object and are called on it: stu1.setName("Ahmet").

Height, this & Private Methods

        


        
Part 27 showed the main idea: private data, public methods that guard it. Height uses the same idea for something a little different. Student's setters only refuse bad values. Height's methods also repair values: give it too many inches, and it turns them into feet by itself, so the object is always in a sensible state. On the way we meet two new tools: the keyword this, and a method that is private.


        
Feet and inches


        
In America, a basketball player is not “2.06 m” tall but 6 ft. 9 in., six feet and nine inches. The rule is at the top of the file:

Another object as a parameter


        
The last method adds one whole Height to another. Its parameter is not an int — it is a Height:

    this.feet += other.feet;
    inches += other.inches;
}

        


        
In the call h1.addHeight(h2) there are two objects at once. this is h1, the one in front of the dot. other is h2, the one in the parentheses:

Only h1 changes. h2 is read, never written: it is still 10 ft 2 in. after the call.


        
Wait — other.feet is a private field, and we are reading it with a dot. Why does that compile? Because the line is written inside the Height class. private means “only code in this class”, not “only this object”. Code inside Height may look at the private fields of any Height. In main, h2.feet is still an error — that is what the two comments under the call are reminding us.


        

          Watch out
          
addHeight does not call simplify(). In the file it works out because 9 + 2 is only 11. Add two heights whose inches go past 11, and the object is no longer tidy:

a.setFeet(6);
a.setInches(9);

b.setFeet(5);
b.setInches(5);

a.printHeight();

One line fixes it: simplify(); at the end of addHeight, as add does. Then the answer is 12 ft. 2 inc. The lesson: every method that changes the inches must call simplify() — that is the promise the class makes.

        


        

          In short
          
this is the object the method was called on; this.inches is always the field, even when a parameter has the same name. A private method is a helper only the class itself can call. Code inside a class can use the private fields of any object of that class — other.feet — because private is about where the code is written. A class keeps its promise only if every method that changes the data keeps it.

The odometer


        
The odometer is the number on a car's dashboard that counts every kilometre the car has driven. A used car with fewer kilometres sells for more — so some sellers illegally wind it back. A well-encapsulated Car class makes that impossible: km is private, there is a getter, there is no setter, and the only way to change it is to drive.


        

          
Car.java

          
public class Car {
    private String plate;
    private double km;

    public void setPlate(String plate) {
        if (plate.length() == 0) {
            System.out.println("Invalid plate!");
        } else {
            this.plate = plate;
        }
    }
    public String getPlate() {
        return plate;
    }
    public double getKm() {
        return km;
    }

    public void drive(double distance) {
        if (distance > 0) {
            km += distance;
        }
    }
}

          Rule
          
Not every field needs a setter. For every field, ask two questions. Should the outside world be able to read it? → write a getter. Should the outside world be able to change it — and with what rule? → write a setter with that rule in its if, or write no setter at all.

          Extras · beyond the four files
          
More Classes to Read and Write

        


        
Nothing new below: private fields, getters, setters with an if, this, a private helper. Each class is a new real-world thing built with exactly the tools of this lesson. Every one is in its own file, used from a main in another file.


        
Designing a class in four steps


        
    
          
  1. What does it have? Those are the fields. Pick a type for each. Make them all private.
    2. 
          
  2. What may never be true? A negative balance, an empty name, minute 75. Those become the ifs in the setters.
    3. 
          
  3. What can the outside read, and what can it change? Getters for the first; setters — or no setter — for the second.
    4. 
          
  4. What can it do? Deposit, drive, add minutes. Those are the other methods. Things that can be worked out (an age, a Fahrenheit value) are methods, not fields.
    5. 
        


        
BankAccount · a read-only balance


        

          
BankAccount.java

          
public class BankAccount {
    private String owner;
    private double balance;

    public void setOwner(String name) {
        if (name.length() == 0) {
            System.out.println("Invalid name!");
        } else {
            owner = name;
        }
    }
    public String getOwner() {
        return owner;
    }
    public double getBalance() {
        return balance;
    }

    public void deposit(double amount) {
        if (amount <= 0) {
            System.out.println("Invalid amount!");
        } else {
            balance += amount;
        }
    }
    public void withdraw(double amount) {
        if (amount <= 0) {
            System.out.println("Invalid amount!");
        } else if (amount > balance) {
            System.out.println("Not enough money!");
        } else {
            balance -= amount;
        }
    }
}

        


        

          
Using it

          
BankAccount acc = new BankAccount();
acc.setOwner("Selin");
acc.deposit(500);
acc.withdraw(120);
acc.withdraw(1000);
acc.deposit(-50);
System.out.println(acc.getOwner() + ": " + acc.getBalance());

          
Console

Invalid amount!
Selin: 380.0

        


        
There is no setBalance. The balance can only change by deposit and withdraw, and both check. A setter does not have to be called set… — any method that changes a field is a mutator.


        
User · a password with no getter


        

          
User.java

          
public class User {
    private String username;
    private String password;

    public void setUsername(String u) {
        if (u.length() == 0 || u.indexOf(" ") != -1) {
            System.out.println("Invalid username!");
        } else {
            username = u;
        }
    }
    public String getUsername() {
        return username;
    }

    public void setPassword(String p) {
        if (p.length() < 6) {
            System.out.println("Too short!");
        } else {
            password = p;
        }
    }
    // no getPassword() on purpose

    public boolean checkPassword(String attempt) {
        return attempt.equals(password);
    }
}

        


        

          
Logging in

          
User u = new User();
u.setUsername("ruzgar 07");
u.setUsername("ruzgar07");
u.setPassword("1234");
u.setPassword("Kedi!2026");
System.out.println(u.getUsername());
System.out.println(u.checkPassword("kedi!2026"));
System.out.println(u.checkPassword("Kedi!2026"));

          
Console
Invalid username!
Too short!
ruzgar07
false
true

        


        
The password can be set and checked, but never read. That is how every real login works: the site can tell you “wrong password”, but no button shows you the right one. equals also cares about capitals, so "kedi!2026" is wrong.


        

          Watch out
          
Before setPassword is called, password is null. attempt.equals(password) is safe: asking a real String whether it equals null just answers false. Written the other way round, password.equals(attempt) calls a method on null — a NullPointerException.

        


        
Thermostat · a value worked out, not stored


        

          
Thermostat.java

          
public class Thermostat {
    private double celsius;

    public void setCelsius(double c) {
        if (c < 5 || c > 30) {
            System.out.println("Choose 5 to 30!");
        } else {
            celsius = c;
        }
    }
    public double getCelsius() {
        return celsius;
    }
    public double getFahrenheit() {
        return celsius * 9 / 5 + 32;
    }
}

        


        

          
Using it

          
Thermostat t = new Thermostat();
t.setCelsius(22);
System.out.println(t.getCelsius() + " C = " + t.getFahrenheit() + " F");
t.setCelsius(45);
t.setCelsius(21.5);
System.out.println(t.getCelsius() + " C = " + t.getFahrenheit() + " F");

          
Console
22.0 C = 71.6 F
Choose 5 to 30!
21.5 C = 70.7 F

        


        
getFahrenheit looks like a getter, but there is no fahrenheit field. Like calculateAge, it is worked out from the one field that is stored. The outside world cannot tell the difference — that is encapsulation too: how the class keeps its data is its own business.


        
Clock · Height with 60 instead of 12


        

          
Clock.java

          
public class Clock {
    private int hours;
    private int minutes;

    public void setHours(int hours) {
        if (hours >= 0 && hours < 24) {
            this.hours = hours;
        }
    }
    public void setMinutes(int minutes) {
        if (minutes >= 0 && minutes < 60) {
            this.minutes = minutes;
        }
    }

    public void addMinutes(int m) {
        if (m > 0) {
            minutes += m;
            simplify();
        }
    }
    private void simplify() {
        hours += minutes / 60;
        minutes = minutes % 60;
        hours = hours % 24;
    }

    public void printTime() {
        if (minutes < 10) {
            System.out.println(hours + ":0" + minutes);
        } else {
            System.out.println(hours + ":" + minutes);
        }
    }
}

        


        

          
The school day

          
Clock c = new Clock();
c.setHours(8);
c.setMinutes(50);
c.printTime();
c.addMinutes(15);
c.printTime();
c.addMinutes(45);
c.printTime();
c.addMinutes(900);
c.printTime();

          
Console
8:50
9:05
9:50
0:50

        


        
Same shape as Height: two int fields, setters with this, and a private simplify with / and %. One extra step — hours % 24 — makes the clock go round past midnight: 9:50 plus 900 minutes (15 hours) is 24:50, which is 0:50. And unlike Height's add, addMinutes checks its argument, so no negative minutes get in.
